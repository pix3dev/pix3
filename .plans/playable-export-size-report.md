# Отчёт: оптимизация размера playable-экспорта

Дата: 2026-08-13. Ветка: `feat/flow-mode`. План и закрытые развилки —
[playable-export-size.md](playable-export-size.md).

## Итог одной строкой

Экспорт того же пинбола: **1.34 MiB → ~0.42 MiB (−69%)** со включённой компрессией,
**→ ~0.98 MiB (−27%)** без неё. Попутно починен реально сломанный `postprocessing`:
нода `PostProcess` в экспортированной игре не работала вообще.

## Что было сделано

### 1. Компрессия выходного файла (самый большой рычаг)

`PlayableHtmlBuildOptions.compress` — чекбокс «Compress output (gzip, self-extracting)» в
диалоге экспорта, по умолчанию включён; у zip-экспорта чекбокса нет (архив и так дефлейтит).
Бандл гзипуется `CompressionStream`, кладётся base64-строкой, а маленький бутстрап
распаковывает его `DecompressionStream` и вставляет код как `textContent` обычного
`<script>`.

Почему именно так, а не blob-URL / `data:` / `new Function`: playable крутят в песочных
iframe с opaque origin и в MRAID-вебвью, где блокируются как раз fetch модуля, blob и
`unsafe-eval`; вставка текста скрипта не требует ничего, чего не требовал сам инлайн-бутстрап.
В репозитории уже был такой же вывод — `classicScriptCompatibilityPlugin` в шаблоне
vite-конфига срезает `type="module"` с выхода. Для этого в `VirtualBundleOptions` добавлен
`format: 'esm' | 'iife'` (в `iife` esbuild инлайнит динамические импорты внутрь IIFE —
проверено на реальном esbuild 0.27.3).

Тонкость, вынесенная в UI и в доки: компрессия уменьшает **файл**, но base64(gzip) повторно
не сжимается, поэтому там, где канал гзипует сам (обычный хостинг, публикация из
prompt-to-playable-flow §7.2 с `Content-Encoding: gzip`, сеть, измеряющая zip), по проводу
станет хуже на треть. Это осознанно выбор на экспорт, а не режим по умолчанию во всём пайплайне.

### 2. Бут плеера больше не клонирует сцену через YAML

`SceneRunner.startScene()` клонирует граф **сериализацией в YAML и повторным парсингом**.
В плеере это означало: entry-сцена парсится дважды, а в бандл затягивается `SceneSaver`
(он импортирует все ~33 класса нод для сериализации) и `yaml.stringify` — ради клона, который
никто не читает. Рантайм-энтри переведён на `loadAndStartScene` (это существующий путь
`changeScene`), `SceneManager` принимает `SceneSaver` опционально (импорт типа, `serializeScene`
без него бросает внятную ошибку).

Это не 14 KiB, а **предусловие**: пока SceneSaver в бандле, ни один тип ноды выпилить нельзя.

### 3. Условная сборка по «упомянуто где угодно»

`RuntimeProjectBuildModel.mentionedNames` — множество всех идентификаторов из текстов
шипнутых сцен/префабов и исходников скриптов проекта (включая id вида `core:Follow`).
Критерий заведомо надмножество нужного: ложное включение стоит килобайты, ложное
исключение — сломанную игру. На нём:

- **Сцены и префабы конвертируются в JSON**, а `yaml` алиасится на шим `JSON.parse` (−96 KiB).
  Конвертация всё-или-ничего: если хоть один файл содержит то, что JSON не выражает, вся
  конвертация отменяется с предупреждением и остаётся настоящий парсер. Проверяется не
  «на глазок»: `.inf` парсится в `Infinity`, который `JSON.stringify` пишет как `null` —
  это молчаливая порча данных, поэтому есть явная проверка JSON-безопасности дерева.
  Скрипт проекта, который сам импортирует `yaml`, тоже отменяет шим.
- **GLTFLoader** → бросающий стаб, если в сборке нет `.glb`/`.gltf` и никто не пишет
  `GLTFLoader` (−42 KiB). Ленивый импорт тут не помог бы: в однофайловой сборке esbuild
  всё равно инлайнит его.
- **Неиспользуемые типы нод и `core:` behaviors** → стабы с теми же именами экспортов
  (генерируются из настоящего исходника, поэтому переименование экспорта не может тихо
  разойтись; если имя всё же потеряется, esbuild валит экспорт с «no matching export»,
  а не выпускает битую игру). −116 KiB на пинболе.
- **Мультиплеер** уехал за генерируемый `virtual:runtime-network` (шаблон spine), так что
  одиночная игра не тащит `src/net/**` (−59 KiB).

Безопасность стабов держится на таблице `src/services/export/strippable-runtime-modules.ts`,
у которой есть **страж от дрейфа**: спека пересчитывает граф value-импортов рантайма по диску
и падает, если у выпиливаемого модуля появился импортёр, не описанный в таблице. То есть
попытка добавить `import { Slider2D }` в модуль, который плеер всегда держит, немедленно
ломает тест, а не экспорт у пользователя.

### 4. Починен `postprocessing` (это был баг, а не оптимизация)

`ScriptCompilerService.onResolve` помечает любой неалиасенный bare-специфаер `external`, а
importmap в экспортированном HTML нет — поэтому `import('postprocessing')` из
`PostProcessingPipeline` в экспорте **никогда не резолвился**, и нода `PostProcess` молча
ничего не делала (`SceneRunner` трактует «не готово» как «рисуй без эффектов»). В
сгенерированном npm-проекте зависимости `postprocessing` вообще не было.

Починка по образцу Spine: новый сеам `setPostprocessingModuleLoader` в рантайме +
генерируемый `virtual:runtime-postprocessing` со статическим импортом, который вендорится
только когда сцена реально ставит `PostProcess`. Проекты без него платят 0 байт; проекты с
ним платят 322 KB и получают работающие эффекты вместо неработающих за 0.

## Замеры

Контрольный прогон продакшн-логикой (транспилированный `strippable-runtime-modules.ts` +
настоящий esbuild; байты по метафайлу):

| конфигурация | сырой JS | gzip | yaml | net | SceneSaver | glTF | postprocessing |
|---|---|---|---|---|---|---|---|
| было (до работ) | 1226 KiB | 314 | 98 KB | 61 KB | 14 KB | 42 KB | 0 (битый) |
| всё упомянуто (худший случай) | 1212 | 311 | 98 KB | 61 KB | 0 | 42 KB | 0 |
| пинбол | 885 | 225 | 0 | 1.6 KB | 0 | 0 | 0 |
| пинбол + нода PostProcess | 1205 | 337 | 0 | 1.6 KB | 0 | 0 | 322 KB |

Для пинбола: 1226 → 885 KiB кода; с компрессией итоговый HTML ~0.42 MiB против 1.34 MiB.
Даже когда выпиливать нечего, экспорт стал на 14 KiB меньше (снятый клон сцены).

Состав того, что осталось: 550 KiB — three.js, и это **пол**, а не «недошейкано»: бандл,
который лишь трогает `WebGLRenderer`, уже 491 KiB (вся библиотека шейдерных чанков).

## Проверено

- `npx tsc --noEmit` — чисто.
- `npm run lint` — чисто (остались 4 предсуществующих warning'а `no-explicit-any` в рантайме,
  к этой работе не относятся).
- `npm run build` — собирается; попутно замечено и починено: сырые тексты `postprocessing`
  (633 KB) и `spine-threejs` (523 KB) попадали в `assets/` и, значит, в PWA-прекеш; они
  перенесены в `assets/export-vendor/**`, который прекеш исключает. Прекеш 41594 → 40464 KiB.
- Тесты: **2579 проходят**. Новые: 15 кейсов на рычаги экспорта
  (`PlayableHtmlBuildService.size.spec.ts` — round-trip gzip-пейлоада, `iife` только при
  компрессии, JSON-сцены и все три причины отката, оба состояния алиасов glTF/postprocessing,
  стабы), 8 на таблицу выпиливания и её стража (`strippable-runtime-modules.spec.ts`),
  4 новых кейса в `ProjectBuildService.spec.ts` (генерируемые network/postprocessing-модули,
  флаг glTF, индекс упоминаний), 2 в `SceneManager.spec.ts` (опциональный saver).
- 22 падения в `packages/pix3-collab-server` — **предсуществующие и не связанные**: нативный
  биндинг `better-sqlite3` не собран под текущий Node (проверено на чистом дереве через
  `git stash`).

## Что осталось (в плане, фаза 4)

1. **Снять `instanceof`-диспатч в `SceneRunner`** — он всё ещё пинит ~90 KiB типов нод
   (Particles3D 24, ScrollContainer2D 13, VirtualCamera3D 10, 3D-меши). Это настоящий
   рефакторинг рантайма с риском для потребителей, поэтому отдельным заходом.
2. **Компрессия ассетов при экспорте** (PNG → WebP, переиспользовать `AssetGenService`):
   `sprites/ph-bg.png` 52.9 KiB → ~12–15 KiB. Пункт уже висит в TODO.md.
3. **Режим «оптимизировать по проводу»** — всё из фазы 2 без компрессии, для публикации.

## Что стоит сделать перед релизом рантайма

Изменения в `@pix3/runtime` (опциональный `sceneSaver`, новый экспорт
`setPostprocessingModuleLoader`, новые `virtual:runtime-*` объявления) обратно совместимы, но
пакет потребляет внешний проект (DeepCore) через yalc — перед публикацией стоит прогнать
`cd packages/pix3-runtime && npm run yalc:publish` + `yalc update` и собрать DeepCore.
В этой сессии не делалось: это отдельный релизный шаг.

Живьём в браузере экспорт не прогонялся (нужен открытый редактор с проектом): вся проверка —
типы, линт, сборка, тесты и контрольный прогон сборочной логики на настоящем esbuild.
Первое, что стоит сделать руками, — экспортировать пинбол с галкой и без и открыть оба файла.
