# Pix3 Flow — режим «промпт → играбельный прототип → ссылка»

**Статус:** фазы 0 и 1 реализованы и проверены живьём (2026-08-12, ветка `feat/flow-mode`);
фаза 2 (публикация) и фаза 3 (фоновая очередь ассетов) не начаты. Контракт рецептов вынесен в
[flow-recipes-contract.md](flow-recipes-contract.md); журнал живой проверки — §11.
**Дата:** 2026-08-11, ревизия 2026-08-12 (принципы §1.2 — итеративность вместо one-shot,
вопросы к пользователю, точечные правки, контекст-менеджмент, инстант-опыт).
Проверено по коду на `fd46d41`.
**Авторы дизайна:** сессия + Fable (архитектурная часть), развилки и принципы — пользователь.

Цель: путь от пустого экрана до расшаренной играбельной ссылки без открытия «настоящего»
редактора — как в Gemini Canvas / Claude Design, но с полноценным движком под капотом.
Пишем промпт → система собирает играбельную сцену → итерации через чат → один HTML или
ссылка.

Рабочие названия режимов: **Flow** (prompt-first) и **Studio** (существующий полный
редактор).

## 1. Рамка, принципы и закрытые развилки

### 1.1 Закрытые развилки (решения пользователя, 2026-08-11)

| Развилка | Решение | Следствие для плана |
| --- | --- | --- |
| LLM-ключи | **BYOK сейчас, серверный metered-прокси потом** | planner-вызов живёт в браузере через существующий `LlmProviderRegistry`; онбординг требует Gemini-ключ или локальный `pix3-agent-bridge`, как Agent-таб сегодня. Metered-прокси — отдельная фаза, вне этого плана |
| Аудитория / публичность | **Приватная бета, только unlisted** | публичный профиль `/u/:username` и модерация UGC — НЕ в v1. Ссылка = секретный slug. Колонка `visibility` в схеме заводится сразу, значение всегда `unlisted` |
| Позиционирование | **Flow — дефолтный первый экран** | welcome перестраивается радикально: prompt-hero это и есть первый экран, списки проектов уезжают во вторичную секцию. Studio = «расширенный режим» |
| Анонимная публикация | **Нет, publish требует логина** | ноль бесхозных артефактов и GC. Download HTML остаётся доступен анониму — это и есть анонимный шаринг |

Прямое следствие решений 2+4: «опубликовать в своём профиле» в v1 реализуется как
приватный список «мои игры» внутри редактора + секретные ссылки. Публичная страница
профиля отложена осознанно, модель данных к ней готова.

### 1.2 Принципы режима (уточнения пользователя, 2026-08-12)

Шесть правил, которые перекрывают любые частные решения ниже. Они сформулированы после
первой версии дизайна и правят её в нескольких местах — там, где это меняло текст,
он переписан.

1. **Цель — НЕ вся игра за один промпт.** Первый ход даёт играбельный скелет и общее
   понимание задумки, дальше — диалог. Успех первого хода измеряется тем, что появилось
   что-то живое, во что можно ткнуть, а не тем, что игра доделана. Это снимает главный
   источник провалов: длинный автономный забег без обратной связи.
2. **Промежуточные состояния играются в уже загруженном рантайме**, а не через сборку
   HTML. Итерация = play mode + hot reload свойств (P0.5, правка видна ≤1 кадра).
   `PlayableHtmlBuildService` вызывается **только** по кнопке Download HTML или Publish.
   Сборка на каждой итерации была бы секундами ожидания на ровном месте.
3. **Агент может спрашивать и уточнять.** Вопрос пользователю — легитимный конец хода, а не
   провал. Промежуточные чекпойнты («сделал управление и врагов — победу считаем по счёту
   или по времени?») лучше, чем угадывание. Механика — тул `ask_user` с вариантами-чипами,
   §5.4.
4. **Только точечные правки файлов.** Полная перезапись существующего файла — исключение,
   требующее причины. Механика уже есть (`str_replace`), не хватает принуждения и того,
   чтобы рецепты состояли из мелких файлов, где точечная правка естественна. §5.4.
5. **Контекст под контролем: измерять, вовремя сжимать, писать доки в проект.** Состояние
   агента живёт не в истории беседы, а в файлах проекта (`design/*.md`). История — расходник,
   который сжимается при достижении ватерлинии. §5.6.
6. **Опыт инстант-приложения при всех возможностях агента.** Ни одного модального ожидания:
   стейдж живёт всегда, ассеты приезжают фоном, ответ агента стримится, тяжёлое (сборка,
   публикация) — только по явной кнопке. Возможности движка не должны ощущаться как
   «тяжёлый редактор, к которому приделали чат».
7. **Вход — не только текст.** В первом же промпте (и в любом последующем) пользователь
   может дать **графические референсы** и **текстовые файлы** — GDD, описание механик,
   таблицу баланса. Это меняет planner на мультимодальный, а стиль ассетов делает
   производным от референса, а не выдуманным. §5.7.

## 3. Продуктовый сценарий

### 3.1 Первый экран

Prompt-hero: большое поле «Опиши игру» + кнопка Make; 4–6 example-чипов («тапалка: лопай
шарики под таймер», «раннер с препятствиями», «playable ad для match-3 с CTA»); ряд
карточек рецептов (обложки из template-каталога) — клик = «этот жанр + мой промпт».
Существующие проекты — вторичной секцией ниже. Анонимному пользователю ничего не мешает:
проект создастся в OPFS без логина.

**Поле принимает вложения** (принцип 7): картинки-референсы и текстовые документы через
paste / drag&drop / picker — вся страница работает дроп-зоной. Логика переиспользуется из
композера чата (`ComposerAttachment`, см. §2), не пишется заново. Приложенные картинки
показываются миниатюрами с **чипом роли** (стиль / объект / макет), которую можно
переключить до отправки; документы — плашкой с именем и размером. Конвейер разбора — §5.7.

### 3.2 Первый ход: 0 → во что можно ткнуть (цель ≤90 с)

Цель первого хода — **не готовая игра**, а живой скелет + общее понимание задумки
(принцип 1). Всё, что дальше, — диалог.

1. **&lt;5 с** — planner-вызов LLM возвращает `PrototypeBrief` (§5.2). На экране «понимаю
   задумку…».
2. **&lt;3 с** — детерминированный экспандер разворачивает рецепт в OPFS-проект: сцены,
   скрипты, плейсхолдер-арты, перекрашенные в палитру брифа, `design/brief.md` +
   `design/progress.md`. **Игра уже запускается** — это скелет жанра, а не пустота.
3. **Стейдж оживает** — Flow-шелл монтирует рантайм (`registerTabHost`) и стартует play.
   Пользователь трогает болванку своей игры, пока агент работает.
4. **Агент берёт ПЕРВЫЙ инкремент**, не весь список: обычно «управление + core-механика».
   Вместо сырого лога тулов — **план-трекер**: «✓ Управление · ● Враги (проверяю…) ·
   ○ Победа/поражение · ○ Графика». Завершённый инкремент = авто-рестарт стейджа.
5. **Ход заканчивается коротким резюме и развилкой**, а не молчаливым «Готово!»:
   «Скелет играется: стрелки двигают героя, монетки собираются. Дальше могу: (1) добавить
   бомбы, (2) сделать победу по счёту, (3) заменить плейсхолдеры на арт». Три чипа — клик
   вместо печати (принципы 3 и 6).
6. **Ассеты фоном** (§6) — плейсхолдеры подменяются, не блокируя ни чат, ни игру.

**HTML на этом пути не собирается ни разу** (принцип 2): всё играется в уже загруженном
рантайме.

### 3.3 Итерация

Чат слева, стейдж справа. «Сделай врагов быстрее» → `set_property` → hot reload без
рестарта. «Добавь звук при прыжке» → скрипт/behavior + верификация. Одна строка статуса на
тул-вызов, полный лог — по клику.

Три вещи отличают этот цикл от «чата с агентом» в Studio:

- **Агент имеет право спросить.** Развилка, которая изменит структуру («победа по счёту или
  по времени?», «врагов спавнить волнами или постоянно?»), выносится пользователю чипами —
  это дешевле, чем угадать и переделать. Правило балансировки, чтобы не превратиться в
  анкету: спрашивать только там, где варианты дают **разную структуру** сцены или скриптов;
  косметику и параметры выбирать самому и сообщать выбор одной строкой («сделал 3 волны —
  скажи, если не то»).
- **Каждый инкремент завершается играбельным состоянием.** Не «написал систему, потом
  проверю» — а «сделал одну вещь, доказал, показал».
- **Стейдж не гаснет.** Пересборка сцены и рестарт play — это доли секунды в уже загруженном
  рантайме; ощущение приложения, а не билд-пайплайна.

### 3.4 «Структура скрыта до востребования» — эскейп-хатчи по нарастающей

1. **Инспектор-лайт** (фаза 4): клик по объекту на паузе → 3–5 «тюнабельных» свойств,
   помеченных рецептом как `tunables`. Слайдер → hot reload.
2. **Open in Studio** — переключение `workspaceMode`: тот же проект, те же сервисы, тот же
   undo-стек, монтируется полный Golden Layout. Обратно так же мгновенно. Предлагается
   проактивно после 2–3 правок вида «подвинь кнопку чуть левее».
3. Файлы и код — только в Studio. Во Flow их не существует как концепции.

### 3.5 Публикация

Шапка Flow: **Download HTML** (существующая команда, работает анонимно) · **Publish**
(требует логин → секретная ссылка + QR) · **Play on device** (существующий relay для
проверки на телефоне до публикации).

### 3.6 Бюджеты отзывчивости (операционализация принципа 6)

Цифры — проектные цели, по ним меряем регрессии; не все проверены (см. §10.5).

| Момент | Бюджет | Чем достигается |
| --- | --- | --- |
| Промпт → первая реакция UI | &lt;300 мс | оптимистичный переход на Flow-шелл, скелет интерфейса до ответа planner'а |
| Промпт → проект развёрнут | &lt;10 с | planner ≈5 с + детерминированный экспандер ≈3 с |
| Промпт → играбельный кадр | ≤90 с | узкое место — первый компил скриптов рецепта (esbuild.wasm), замерить |
| Правка параметра → видно в игре | ≤1 кадр | hot reload P0.5, **без рестарта** |
| Структурная правка → видно в игре | &lt;2 с | рестарт play в загруженном рантайме, без сборки |
| Сборка HTML | по кнопке | и только по кнопке (принцип 2) |
| Генерация ассета | не блокирует | фоновая очередь + подмена плейсхолдера (§6) |

Правило, следующее из таблицы: **ни одной модалки на пути итерации**. Прогресс-диалоги
допустимы только там, где пользователь сам запросил долгую операцию — Download HTML и
Publish.

### 3.7 Три пользовательских трека

**A — hyper-casual тапалка (маркетолог, без опыта).** «Тапаешь по падающим монеткам,
промахнулся по бомбе — проигрыш». Рецепт `tapper-2d`, скелет играется через ~30 с (серые
кружки падают, тап работает). Агент: перекрасил, добавил бомбы, win по 50 монеткам. Фоном
приехали спрайты. Итерации: «бомб побольше», «звон при сборе». Publish → ссылка коллегам.
Studio не открывался ни разу.

**B — платформер (хоббист).** «Лягушка прыгает по кувшинкам над водой». Рецепт
`platformer-2d` (rapier, прыжок, платформы, `core:CameraBrain`). Ключевая сложность —
левел-дизайн: уровень держится **данными на нодах** (правило скилла «конфиг уровня — в
сцене, не в коде»), агент расставляет платформы `create_node`/`set_property`.
«Первая яма слишком широкая» → hot reload. На третьей итерации «хочу сам подвигать» →
Open in Studio → мышкой → назад во Flow → Download HTML.

**C — playable ad с CTA (продюсер; целевая аудитория ROADMAP 💰).** «Playable для match-3:
5 ходов, потом CTA в стор». Рецепт на базе существующего `playable-2d` (tap-to-start
аудио-гейт + CTA-экран + `PlayableSDK.openStore()` с MRAID/DAPI). Особенность трека —
**бюджет размера**: Flow показывает size-report (уже считается) и предупреждает при
&gt;3–5 MB. Итерации про конверсию: «CTA крупнее и пульсирующей» (`core:PunchScale`).
Валидацию ad-сетей Flow **потребляет**, а не реализует — это ROADMAP P0.6.

## 4. Архитектура: Flow как второй shell

**Решение: отдельный shell-режим поверх тех же сервисов.** Отклонены:

- **«Новая панель в Golden Layout»** — не выполняет главное продуктовое требование по
  определению: пользователь видит доки, табы, меню. Agent-панель (`agent-stack` в
  [LayoutManager.ts](../src/core/LayoutManager.ts)) уже есть — это и есть данный вариант, и
  это другой продукт.
- **«Отдельная точка входа, как player.html»** — Flow нужны ВСЕ тяжёлые подсистемы
  (`AgentToolRegistry` тянет `SceneManager`, `CommandDispatcher`, `ScriptCompilerService`
  с esbuild.wasm, `GamePlaySessionService`, image-gen), то есть второй бутстрап DI-графа и
  вечная борьба с дивергенцией. Убийца варианта: **Open in Studio становится перезагрузкой
  страницы** с сериализацией проекта, беседы агента и undo-стека вместо переключения
  компонента. `player-main.ts` не прецедент — он не использует DI-граф редактора вообще.

| | Shell-режим (выбран) | Отдельный entry | Панель |
| --- | --- | --- | --- |
| Стоимость до первого результата | **M** | L | S |
| Риск дивергенции | низкий (один DI-граф) | **высокий** | нулевой |
| Продуктовое качество | полное | полное | **не достигается** |
| Open in Studio | переключение компонента | перезагрузка + handoff | n/a |

Механика: `appState.ui.workspaceMode` → `pix3-editor-shell` рендерит либо `layout-host` +
`LayoutManagerService` (лениво, при первом входе в Studio), либо `<pix3-flow-shell>`.
Flow-шелл = стейдж (свой `div` через `registerTabHost`) + чат (`pix3-agent-chat-panel`) +
шапка (title, план-трекер, Download/Publish/Device/Open in Studio). Все мутации идут через
тот же `CommandDispatcher`/`OperationService` — undo/redo и hot reload работают бесплатно.

**Главный технический риск** — скрытые зависимости от `isLayoutReady`/панельных событий.
Найдено грепом: `isLayoutReady` фигурирует в [RouterService.ts](../src/services/core/RouterService.ts),
[LayoutManager.ts](../src/core/LayoutManager.ts), [AppState.ts](../src/state/AppState.ts),
[pix3-editor-shell.ts](../src/ui/pix3-editor-shell.ts) — аудит обязателен при ленивой
инициализации. План Б, если аудит вскроет много завязок: инициализировать LayoutManager
скрыто (нулевой размер / `display:none`) — Flow всё равно получает свой шелл, а стоимость
простаивающего редактора близка к нулю (render-on-demand, см. CLAUDE.md).

**Скриншоты для агента:** `viewport_screenshot` во время play снимает канвас игры
([AgentToolRegistry.ts:846](../src/services/agent/AgentToolRegistry.ts#L846)) — verify-цикл
не зависит от наличия редакторского вьюпорта. Edit-mode скриншоты во Flow v1 недоступны;
если понадобятся — монтировать `src/ui/viewport/editor-tab.ts` скрыто (**не проверено**, что
он монтируется вне GL-контейнера; искать завязки на GL resize-события).

## 5. Надёжность: как агент выдаёт играбельное с первого промпта

### 5.1 Что говорят измерения

[agent-eval-results.md](agent-eval-results.md) — готовый natural experiment. Раунд 1:
сборка по GDD с нуля = FAIL (агент пишет скрипты в вакууме, не запускает, обрывается по
капу итераций). Раунд 3: **та же дешёвая модель**, но (а) стартовый шаблон `minigame-2d`,
(б) `game_input`/`game_observe` как инструменты доказательства геймплея, (в) verify-нуджи
харнесса, (г) скилл с engine-ловушками → **S1 и S3 PASS** с доказанным движением и
win/lose. S4 (дизайн-решение) — PASS, но ~35 мин и ~2.1M входных токенов.

Вывод: переход FAIL→PASS дала связка «детерминированный скелет + инструменты доказательства»,
а не смена модели или добавление оркестратора. Отсюда — три слоя ниже.

**Полный декларативный blueprint нод/скриптов отклонён** осознанно: игровая логика не
декларативна без visual-scripting-эквивалента (прямой анти-скоуп ROADMAP §7), а стоимость
контракта «на все жанры» — L+ при недоказанном выигрыше против «рецепт + агент», у которого
выигрыш измерен.

### 5.2 Слой 1 — Рецепты (детерминированные 80%)

Расширение `src/templates/projects/`: `recipe-tapper-2d`, `recipe-runner-2d`,
`recipe-platformer-2d`, `recipe-arena-2d`, `recipe-playable-ad`. Рецепт = обычный шаблон
плюс контракт для агента:

- Полностью **играбельный** микро-скелет: меню → игра → win/lose, управление, счёт.
  Нейтральные плейсхолдер-арты с ролями.
- `design/recipe.md` — машиночитаемая карта: плейсхолдеры и их роли; тюнаблы и где они
  лежат (нода / component config); как добавить новый тип entity; чего НЕ трогать.
- Тюнаблы живут **на нодах и в component config**, чтобы агент (`set_property`) и
  инспектор-лайт били в одно место.
- **Мелкие файлы с одной ответственностью** (принцип 4): `PlayerController.ts`,
  `Spawner.ts`, `ScoreHud.ts`, `GameRules.ts` — не один `GameManager.ts`. Это не стиль, а
  требование надёжности: в монолитном файле любая правка провоцирует полную перезапись, а
  перезапись измеримо теряет предыдущие правки. Ориентир — файл влезает в один экран
  внимания модели (~100–150 строк).
- **Расширяемость важнее полноты.** Рецепт не пытается угадать игру; он даёт каркас и
  **явные точки расширения**, описанные в `recipe.md` («новый тип врага = добавить запись в
  `enemies` + спрайт; спавнер подхватит»). Агенту дешевле дописать в объявленную точку, чем
  изобрести структуру.

Инфраструктура вся готова — работа контентная (написать 3–5 хороших мини-игр), и она
**переиспользуется как обычные шаблоны** в Studio.

### 5.3 Слой 2 — PrototypeBrief (лёгкий IR, один вызов)

`PrototypeBootstrapService` делает один structured-output вызов через существующий
`LlmProviderRegistry`:

```ts
interface PrototypeBrief {
  title: string;
  pitch: string;                    // одна строка для шапки
  recipeId: string;                 // из каталога рецептов
  style: { palette: string[]; artStyle: string; mood: string };  // токены для ВСЕЙ генерации
  entities: Array<{
    role: 'player' | 'enemy' | 'collectible' | 'obstacle' | 'background' | 'ui' | string;
    name: string;
    assetSpec: { prompt: string; sizeHint?: number };
  }>;
  tunables: Record<string, number | string | boolean>;  // маппится на точки рецепта
  winLose: { win: string; lose: string };
  increments: string[];             // 3–5 шагов → design/progress.md
  ctaUrl?: string;                  // только playable-ad
  // Вложения первого промпта (§5.7). Пути — уже сохранённые файлы проекта, не блобы.
  references?: Array<{
    path: string;                   // res://references/... или design/source/...
    kind: 'image' | 'doc';
    role?: 'style' | 'content' | 'layout';   // только для image
    note?: string;                  // что из него взято (токены стиля / раздел GDD)
  }>;
}
```

`style` при наличии style-референса **заполняется из него** (квантованная палитра +
vision-токены), а не выдумывается моделью.

Детерминированный экспандер: создать OPFS-проект из `recipeId`
(`createNewProjectWithOptions`), применить `tunables` через property-schema, tint
плейсхолдеров палитрой (canvas-tint при копировании), записать `design/brief.md` и
`design/progress.md` (формат чек-листа, который скилл `game-prototype` уже требует и умеет
резюмить между сессиями). **Fallback:** planner вернул мусор или неизвестный `recipeId` →
берём ближайший по типу управления рецепт и отдаём промпт агенту как есть; хуже статус-кво
не становится.

### 5.4 Слой 3 — Исполнитель: существующий цикл с proto-пресетом

- **Verify-нудж → verify-гейт.** Сейчас непроверенная мутация геймплея даёт **один** нудж и
  дальше ход закрывается ([AgentChatService.ts:613](../src/services/agent/AgentChatService.ts#L613),
  флаги `unverifiedGameMutation` / `gameVerifyNudged`). Во Flow ход не закрывается, пока:
  (а) `compile_scripts`/`check_scripts` чистые, (б) `read_errors` после `play_start` пуст,
  (в) `game_input`-вердикт по core-механике инкремента пройден — до K попыток, затем
  **честный fail-репорт** («не смог доказать X, вот что видел»). Никогда — молчаливое
  «Готово!».
  **Важное исключение (принцип 3):** гейт НЕ должен ловить ход, который заканчивается
  вопросом к пользователю. Вызов `ask_user` снимает verify-долг так же, как успешный
  `game_input` — иначе агент, честно упёршийся в развилку, будет насильно догоняться в
  бессмысленную верификацию. Реализация: `ask_user` в той же ветке, что очистка
  `unverifiedGameMutation`.
- **Тул `ask_user` — вопрос как легитимный конец хода.** Контракт:
  `ask_user({ question, options?: string[], allowFreeform?: boolean })` → ход завершается,
  UI рисует вопрос и варианты чипами, ответ приходит следующим сообщением пользователя.
  Правило в скилле: спрашивать только про развилки, меняющие **структуру** сцены/скриптов;
  косметику и параметры выбирать самому и сообщать выбор. Без этого правила режим
  выродится в анкету и убьёт «инстант».
- **Точечные правки принудительно (принцип 4).** `str_replace` есть и описан правильно, но
  измерено, что модель всё равно уходит в полную перезапись (eval S4: трижды переписала
  большой файл идентичным содержимым, считая, что поменяла константу). Меры:
  (1) **гард в `fsWrite`** — перезапись СУЩЕСТВУЮЩЕГО файла больше N КБ отклоняется с
  сообщением «используй `str_replace`; для полной замены передай `overwrite:true` и
  причину»; (2) полная перезапись без причины считается сигналом для loop-breaker'а;
  (3) **конструктивная мера, которая работает лучше запретов:** рецепты авторятся из
  МЕЛКИХ файлов с одной ответственностью (`PlayerController.ts`, `Spawner.ts`,
  `ScoreHud.ts`), а не одного `GameManager.ts` — тогда точечная правка естественна, а
  перезапись мелкого файла безвредна. Это требование к рецептам в §5.2.
- **Инкремент — единица работы, и он же граница беседы.** Агент берёт ОДИН инкремент за ход
  (принцип 1), доводит до играбельного и доказанного, отчитывается — и на границе инкремента
  контекст сжимается, а состояние передаётся через доки проекта (§5.6). Измерено (eval,
  advisor-раздел): та же задача, на которой длинная беседа кружила, в свежей беседе с
  компактным брифом решается без подсказок. Это самый дешёвый крупный выигрыш надёжности в
  плане.
- **Прогресс-события** — тул-вызовы мапятся в статусы план-трекера по чек-боксам
  `design/progress.md`; шумные детали сворачиваются.
- Пресет: скилл `game-prototype` инжектится первым, `maxToolIterations` повышен (у дешёвых
  моделей разведка съедает ~15 итераций), «budget your exploration» продублирован в system
  prompt (открытый пункт бэклога раунда 3).

### 5.5 Ранжирование «надёжность на единицу работы»

1. Рецепты — M, выигрыш доказан эмпирически (FAIL→PASS).
2. Verify-гейт — S, механизм готов на ~70%.
3. Инкремент = единица работы + свежая беседа на инкремент — S, атакует измеренную причину
   зацикливания.
4. Brief + экспандер — S/M, убирает «первые 15 итераций разведки» и даёт мгновенный первый
   кадр.
5. `ask_user` + гард на перезапись файлов — S каждый.
6. Embeddings/семантика библиотеки — L, отложено (§6).

### 5.6 Контекст и доки проекта как память агента (принцип 5)

**Что уже есть:** `contextWindow` на модель в провайдерах, отслеживание заполнения контекста
и cached-сегмента в chat-панели, `cache_control`-breakpoints. То есть **измерение**.
**Чего нет:** ни сжатия, ни тримминга истории — `AgentChatService` копит сообщения
неограниченно, пока провайдер не откажет.

**Модель памяти: состояние живёт в файлах проекта, история беседы — расходник.**

| Файл | Содержимое | Кто пишет |
| --- | --- | --- |
| `design/brief.md` | Задумка, жанр, стиль, сущности, win/lose — из `PrototypeBrief` | экспандер, затем агент при смене задумки |
| `design/progress.md` | Чек-лист инкрементов с состоянием; что доказано и чем | агент после каждого инкремента (уже требуется скиллом) |
| `design/decisions.md` | Принятые развилки и ответы пользователя на `ask_user` — чтобы не переспрашивать | агент при закрытии развилки |
| `design/recipe.md` | Карта рецепта: плейсхолдеры, тюнаблы, чего не трогать | автор рецепта (статично) |

**Цикл сжатия:**

1. Заполнение контекста считается из уже доступных `inputTokens` и `contextWindow` модели.
2. **Ватерлиния ~60%** — агенту инжектится «допиши `design/progress.md`, закругляй
   инкремент». Мягкая мера, работы не теряет.
3. **Ватерлиния ~75% или конец инкремента** (что раньше) — **компакция**: агент пишет доки,
   беседа начинается заново с `brief.md` + `progress.md` + `decisions.md` в стартовом
   контексте. Для пользователя это невидимо: тот же тред в UI, разделитель «— контекст
   сжат —».
4. Аварийный порог ~90% — жёсткий тримминг старых tool-результатов (они самые объёмные и
   самые бесполезные задним числом), чтобы ход вообще не упал.

Обоснование ватерлиний, а не «сжимать в конце»: измерено, что источник зацикливания —
загрязнённый контекст, а не сложность задачи (eval, advisor-раздел). Компакция на **границе
инкремента** — это то же самое, что «свежая беседа на инкремент», просто с явным
пределом сверху для длинных инкрементов.

**Взаимодействие с кэшем:** компакция обнуляет prefix-кэш, поэтому она привязана к границе
инкремента, а не к произвольному сообщению. Внутри инкремента префикс (system + скиллы +
`recipe.md` + tool-список) обязан оставаться **байт-в-байт стабильным** — любая
«динамическая» вставка в system prompt (время, счётчики, текущая сцена) убивает кэш и
удорожает прогон в разы. Это требование к proto-пресету, а не пожелание.

### 5.7 Вложения на входе: референсы и документы (принцип 7)

Пользователь может приложить к первому промпту (и к любому последующему) картинки-референсы
и текстовые файлы — GDD, описание механик, таблицу баланса.

**Что уже готово:** композер принимает картинки и текст через paste/drop/picker;
`AgentVisionService` выдаёт по картинке стилевые токены в формате, готовом для
generate-промпта; есть `analyze_image`. **Что делать:** проводка в prompt-hero, персистенция
и мультимодальный planner.

#### Железное правило: вложение немедленно становится файлом проекта

Всё приложенное сохраняется **до** первого вызова модели:

| Вход | Куда | Зачем |
| --- | --- | --- |
| Картинки | `res://references/<имя>` | становятся обычными ассетами: видны в Assets, доступны `generate_asset`/`analyze_image`, переживают перезагрузку |
| Текстовые документы | `design/source/<имя>.md` | первоисточник задумки, читается агентом по секциям |
| Извлечённое | `design/brief.md`, `design/style.md` | нормализованный результат разбора |

Причина жёсткости правила — принцип 5: **всё, что живёт только в истории беседы, исчезает
при компакции.** Референс, приложенный на первом ходу, должен быть доступен агенту на
двадцатом; единственный способ это гарантировать — файл в проекте.

#### Разбор картинок: роль референса решает всё

Урок eval S2 (измерено): генератор **копирует композицию** референса — в спрайт машины
приехала вся трасса с четырьмя машинами. Поэтому картинка не «референс вообще», у неё есть
роль, и роли обрабатываются по-разному:

| Роль | Как используется | Чего НЕ делаем |
| --- | --- | --- |
| **style** (мудборд, скриншот чужой игры) | `AgentVisionService` → токены стиля → `brief.style` → **словами** в каждый generate-промпт | никогда не передаём саму картинку в `references[]` генератора |
| **content** (конкретный объект: «вот такой герой») | картинка идёт в `references[]` генератора как есть — тут копирование композиции желательно | не тянем из неё палитру всей игры |
| **layout** (мокап экрана, схема уровня) | `analyze_image` → структурное описание → подсказка агенту при сборке UI/уровня | не отдаём в генератор ассетов вообще |

Роль определяется автоматически (vision-классификатор в том же вызове, что и токены) и
**показывается пользователю чипом с возможностью переключить** — это дешевле, чем ошибиться
молча, и укладывается в принцип 3.

Палитру берём **детерминированно** — квантованием цветов картинки в браузере, а не «спроси
у модели hex-коды»: быстрее, бесплатно и точнее. Vision-вызов остаётся для того, что
квантованием не берётся (стиль рендера, линия, освещение, настроение).

#### Разбор документов: не инлайнить

GDD на 20 страниц, вставленный в промпт целиком, — это ровно та ошибка, которая в eval S1
сожгла 472K входных токенов (полные референс-доки, пересылаемые каждую итерацию). Поэтому:

1. Документ **пишется в `design/source/`** и не попадает в контекст целиком.
2. Planner получает **бюджетированную выжимку**: заголовки + первые N КБ + всё, что похоже
   на механики/сущности/условия победы. Если документ большой — отдельный дешёвый
   summarize-вызов, результат в `design/brief.md`.
3. Агент дочитывает нужное **по секциям** через `fs_read` — тот же паттерн, что
   `read_skill(id, section)`, и то же правило бюджета разведки в скилле.
4. Противоречия документа и промпта разрешает пользователь через `ask_user`, ответ ложится
   в `design/decisions.md`.

#### Влияние на выбор рецепта

Вложения — это дополнительный вход planner'а, и часто более надёжный, чем короткий промпт:
GDD, где написано «match-3 с ограничением ходов», задаёт `recipeId` точнее, чем фраза
«сделай игру как у конкурентов». Приоритет при конфликте: явный промпт > документ > картинка.

#### Вложения в последующих ходах

Тот же путь без исключений: «вот так должна выглядеть кнопка» на десятом ходу → картинка
падает в `res://references/`, получает роль, и дальше работает как content-референс для
`generate_asset`. Никакой отдельной ветки кода.

## 6. Ассеты: placeholder-first, generate-behind

1. **T0:** рецепт содержит нейтральные арты по ролям; экспандер перекрашивает их палитрой
   брифа. Игра сразу выглядит «намеренно», а не серой.
2. **T0+фон:** `AssetJobQueueService` — очередь из `entities[].assetSpec`, конкуренция 2–3,
   каждое задание = существующий пайплайн `generate_asset` (генерация + resize/trim/
   bg-removal уже встроены). По готовности **подмена** через
   `UpdateObjectPropertyOperation` на texture-свойство (undoable, hot reload работает) +
   `viewportRenderService.requestRender()`. Агенту даётся `queue_asset` вместо синхронного
   ожидания — чат не встаёт на 40 секунд, статус приезжает следующей итерацией.
3. **Библиотека прежде генерации, но честно про её размер.** Стор сегодня — 7 items
   ([store-seed.ts](../src/services/library/store-seed.ts)), поиск — substring + токен-AND
   ([library-search.ts](../src/services/library/library-search.ts)). Правило v1: перед
   `queue_asset` — поиск по личной библиотеке и стору по контролируемому словарю
   ролей-тегов (тот же enum, что `entities[].role`); точный тег-матч → вставка через
   `LibraryInsertService`; нет → генерация, и (opt-in) сохранение удачного в личную
   библиотеку с ролью-тегом. Библиотека растёт от использования. Embeddings — до стора в
   сотни items; манифест уже несёт `tags`/`description`/`categoryPath`
   ([library-types.ts](../src/services/library/library-types.ts)), добавится серверной
   фичей без ломки клиента.
4. **Консистентность стиля:** токены `style` инжектятся в каждый generate-промпт. Урок eval
   S2 обязателен: **не передавать полносценные референсы** в `references[]` — генератор
   копирует композицию (в спрайт машины приехала вся трасса с 4 машинами); стиль — словами,
   референс — только первый *сгенерированный* ассет для последующих. Когда пользователь дал
   свои референсы (§5.7), источник токенов — они: style-референс питает `brief.style` и
   через него все генерации, content-референс идёт в `references[]` точечно для СВОЕГО
   ассета и ничьего больше.

## 7. Хранение и публикация

### 7.1 Хранение

- **Аноним:** OPFS-проект — ноль запросов, ноль трения, работает сегодня. Риск eviction
  браузером: `navigator.storage.persist()` + мягкий баннер «работа живёт в этом браузере,
  войди чтобы сохранить в облако».
- **Логин просим ровно в трёх местах:** Publish, «Save to cloud», «открыть на другом
  устройстве».
- Привязка OPFS-проекта к аккаунту: есть `CloudProjectService.createProjectFromTemplate` +
  sync-сервисы, но **единой операции «adopt anonymous project» не найдено** — вероятно
  придётся дописать (фаза 2).

### 7.2 Публикация (новая подсистема)

Ключевое упрощение: артефакт = тот самый **single-file HTML** из
`PlayableHtmlBuildService.buildPlayableHtml`. Сервинг тривиален — один файл, никакой
распаковки, никаких ассет-деревьев. Существующий `share_token` в `projects-router.ts` — это
шаринг **collab-проекта**, не игры; переиспользовать нельзя.

**Сервер** — `packages/pix3-collab-server/src/core/publish/` по образцу `core/library/`:

- `published_games (id, owner_id, slug UNIQUE, title, description, visibility, cover_path,
  current_version, created_at, updated_at)` + `published_game_versions (id, game_id,
  version, artifact_path, size_bytes, created_at)`. `visibility` в v1 всегда `unlisted`,
  slug — длинный случайный (секретная ссылка).
- Файлы в `PUBLISH_STORAGE_DIR` (паттерн `LIBRARY_STORAGE_DIR`), артефакт хранится gzip'ом,
  отдаётся с `Content-Encoding: gzip`.
- Роуты: `POST /api/publish` (requireAuth, multipart: html + cover + метаданные, лимит
  ~10–20 MB, квота — например 20 игр × 5 последних версий с подчисткой старых),
  `PATCH /api/publish/:id`, `DELETE /api/publish/:id`, `GET /api/publish/mine`.
- **Сервинг:** `GET /p/:slug` → 302 на `/p/:slug/v/:n` (immutable cache) → HTML.
  **Обязательно отдельный origin** (`play.pix3.dev` на той же машине — cloud+rooms уже
  соседствуют): опубликованный HTML содержит произвольный JS и не должен исполняться на
  origin с auth-куками cloud.pix3.dev. CSP строгая — экспорт уже self-contained, внешних
  запросов не делает. CDN не нужен на старте (один хост + кэш-заголовки); появится трафик —
  CloudFlare перед поддоменом без изменений кода.
- Публичная страница профиля `/u/:username` — **не в v1** (решение: только unlisted).
  Вместо неё `GET /api/publish/mine` + список «мои игры» в редакторе.
- Обложка — скриншот play-канваса при публикации.

**Клиент:** `GamePublishService` (`src/services/cloud/`) + `PublishGameCommand`
(`src/features/project/`, рядом с `ExportPlayableHtmlCommand`): build → прогресс-диалог
(переиспользовать [PlayableExportProgressDialogService.ts](../src/services/export/PlayableExportProgressDialogService.ts))
→ upload → диалог со ссылкой и QR. Кнопка во Flow-шапке и в меню Studio (команда попадёт в
меню автоматически через `CommandRegistry`).

**Preview-relay не трогаем** — он остаётся «живой игрой на устройстве во время итерации»
(требует открытый редактор-host); publish — персистентный снапшот. Переиспользования между
ними нет, и это правильно.

### 11.2 Баги, найденные догфудингом (все починены)

| Симптом | Корень |

| Скрипты нового проекта не компилировались | компиляция триггерилась только переходом статуса в `ready`; создание проекта поверх открытого статус не меняет |
| Компонент терял дефолты своего класса | `SceneLoader` **заменял** конфиг вместо слияния: поле, которого нет в YAML, приходило `undefined` (шаг сетки 100 становился 1) |
| Агент жёг ~9 итераций на stop/start | `play_start` возвращал `ok:false`, когда игра уже идёт, — а во Flow это норма |
| Агент гадал после неудачного `set_property` | тул возвращал голое `{ok:false}` без причины |
| Ход упирался в кап молча | нет финального текстового ответа |
| Агент чинил уже починенное | `read_errors` отдавал протухшие диагностики компилятора |

| Панель чата наезжала на стейдж | `min-width: auto` у флекс-элемента панели |
| Проект уезжал в Studio сразу после создания | режим выбирается до того, как у проекта появляется id |
