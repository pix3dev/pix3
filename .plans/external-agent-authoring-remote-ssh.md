# Дополнение: внешний агент и проект на сервере, Pix3 в локальном браузере

Status: **принято 2026-09-25** (решения — основной план, §11.1); спайк этапа 1 начат · Date: 2026-09-25 · Ревизия 2 (разбор внешнего ревью)

Дополняет [external-agent-authoring.md](external-agent-authoring.md), прежде всего §1.2,
§5 C–D и §6. Основной план не изменён. Команды и протокол ниже — проектируемый интерфейс,
не инструкция по уже доступной функции.

## 1. Задача и предлагаемое решение

Пользователь открывает папку игры на удалённом сервере через VS Code Remote SSH. Claude Code
работает там же. Pix3 и Chrome работают на компьютере пользователя. Единственная рабочая папка
остаётся на сервере: без локального checkout, Git-синхронизации и обязательного сетевого диска.

Предлагается добавить в CLI сервер доступа к проекту, а в редактор — backend `workspace`.
Через один проброшенный порт редактор читает и сохраняет файлы, получает уведомления об изменениях
и обслуживает MCP-вызовы агента. Игра исполняется в локальном браузере, на его GPU.

```text
Удалённый сервер                         Компьютер пользователя

Claude Code ─ stdio MCP ─┐
                        │
                    Pix3 CLI ← SSH → Pix3 в браузере
                        │             редактор + исполняемая игра
                    папка игры

Chrome DevTools MCP ─── отдельный существующий SSH-туннель → локальный Chrome
```

SSH обеспечивает транспорт; Pix3 не хранит SSH-ключи и не устанавливает SSH-соединения.
Тот же backend применим к локальной папке через CLI без SSH, но локальный FSA-путь сохраняется.

## 2. Почему основной план не покрывает этот случай

В §1.2 основного плана браузер уже имеет FSA-handle на ту же физическую папку, где работает агент.
Проброс HTTP-порта позволяет связаться с CLI, но не делает удалённую папку доступной системному
пикеру браузера. Даже если отдавать сам редактор удалённым Vite, пикер остаётся локальным.

Nonce-challenge основного плана тоже не проходит: браузер не может независимо прочитать файл
на сервере. Выдать nonce через тот же HTTP API — круговая проверка, не доказательство доступа
к той же папке. Workspace-путь должен иметь собственное подтверждение подключения.

§1.2 уже упоминает workspace-адаптер как возможную работу после фазы 3. Здесь предлагается
сделать его обязательным условием заявления о поддержке Remote SSH, сохранив локальные фазы
основного плана. Это не возврат к headless-хосту: игра и редактор остаются в окне человека.

Перед подготовкой дополнения проверены канонические разделы `docs/pix3-specification.md`
о локальной файловой интеграции и `docs/architecture.md` → File System Services / File Watch
Service. Они описывают FSA и polling, а не удалённый backend: предлагаемое расширение нужно
внести туда при реализации, не выдавать текст дополнения за действующий контракт продукта.

В текущем рабочем дереве `ProjectStorageService` маршрутизирует `local` и `cloud`; `getFileHandle`
у облачного пути уже допускает `null`. `ProjectService` всё ещё содержит работу с directory/file
handles. В `packages/pix3-cli/src/` уже есть код `new`, `mcp` и loopback link-server, хотя заголовок
основного плана говорит «не начат». Это наличие исходников, не подтверждение готовности или
публикации функции. Удалённый файловый API и команда `dev` в просмотренном CLI отсутствуют.

## 3. Пользовательский процесс

### Первое подключение

1. Пользователь открывает удалённую папку игры в VS Code и запускает в её терминале:
   ```bash
   npx @pix3/cli@<версия-проекта> dev --port 8490
   ```
   В agent kit команда должна содержать настоящую закреплённую версию, не placeholder.
2. CLI слушает только `127.0.0.1` сервера, показывает имя проекта, путь, порт и одноразовый секрет
   подключения. Не пытается открыть браузер на сервере. При занятом явно указанном порте сообщает
   ошибку; не меняет порт молча.
3. Пользователь пробрасывает порт через панель Ports в VS Code. Если локальный порт отличается,
   использует фактический локальный адрес. Проброс можно сохранить настройкой
   `remote.restoreForwardedPorts` ([VS Code Remote SSH](https://code.visualstudio.com/docs/remote/ssh#_forwarding-a-port-creating-ssh-tunnel)).
4. В существующем окне/PWA Pix3 выбирает «Подключить проект», вводит локальный адрес и секрет.
   Подтверждение показывает проект и путь, заявленные сервером. FSA-пикер не открывается.
5. Редактор загружает проект. Claude Code запускается в той же папке; MCP-конфигурация kit
   направляет его к серверу этого workspace.

Ввод адреса и секрета — основной путь для PWA: он не предполагает, что ссылка из терминала
откроется в установленном окне. Ссылка для обычной вкладки может быть последующим удобством,
но не условием работы.

### Следующие сеансы

Пользователь открывает SSH-сессию, запускает `pix3 dev`, открывает проект из «Недавних».
Запись хранит endpoint и идентичность workspace, а не FSA-handle. После краткого обрыва туннеля
соединение восстанавливается автоматически. После перезапуска CLI сохранённое подключение
может восстанавливаться только при безопасно сохранённом и проверенном credential (§5).
При недействительном credential редактор просит новый секрет, а не выбрать папку.

Работа редактора не зависит от жизни Claude Code: остановка или перезапуск агента не закрывает
файловый доступ. Остановка `pix3 dev` разрывает его явно.

## 4. Запуск, тестирование и отладка

### Один цикл агента

1. Агент читает и изменяет файлы непосредственно на сервере.
2. Запускает доступную по основному плану проверку файлов (`pix3 check` после её реализации).
3. Вызывает `play_start`, `play_restart` или `game_run` через MCP с ожиданиями `expect`.
4. CLI и редактор выполняют барьер §5 D основного плана: сверяют диск и ожидания агента,
   загружают изменения, завершают компиляцию, сверяют реально загруженные хеши.
5. Игра запускается в локальном браузере. Агент получает состояние, логи, ошибки и изображения,
   выполняет игровые действия, исправляет файлы и повторяет прогон.

Сохраняются ошибки `disk_differs_from_agent`, `sync_timeout`, `load_failed`, `pending_external`,
поля `revision`, `matchesAgent`, `matchesDisk`, `changedDuringRun` и ограничения гарантий
основного плана. Удалённый backend **не обещает неизменяемого снимка на весь прогон**:
ленивая загрузка ресурсов и внешние записи остаются возможными. События watcher не заменяют
полную сверку перед запуском. Timeout барьера должен быть настраиваемым в пределах общего
deadline вызова: прежние ~5 секунд нужно проверить на SSH, не переносить как константу.

Наблюдающие инструменты не останавливают игру и возвращают её ревизию и `stale`.
Обычная кнопка Play должна проходить эквивалентную синхронизацию без ожиданий агента.
Ввод и рендеринг локальны; сетевые обращения нужны для файлов, инструментов и загрузки ресурсов.

| Канал | Назначение |
| --- | --- |
| Pix3 MCP через workspace | Play, routines, состояние сцены/игры, ошибки, логи, скриншоты |
| Chrome DevTools MCP через существующий туннель | DOM, сеть, консоль, браузерная диагностика |
| DevTools человека | Breakpoints, пошаговое выполнение, профилирование |

Порт 9222 не нужен для файлового доступа и не заменяет его. Существующий настроенный пользователем
туннель к локальному Chrome сохраняется; CLI не открывает отладочный порт автоматически.
Отсутствие DevTools MCP не должно мешать обычному циклу Pix3 MCP.

Для отладки игровых скриптов нужны source maps с содержимым исходников и устойчивыми именами
`scripts/Player.ts`, корректные строки в stack traces после перекомпиляции. Это отдельный критерий
приёмки, а не следствие HTTP-доступа к папке. Подключение debugger из удалённого VS Code к локальному
Chrome и mapping путей — последующий сценарий, не обязательная настройка первого запуска.

## 5. Архитектура и границы доверия

### Сервер workspace и MCP

`pix3 dev` владеет файловым API, наблюдением, идентичностью workspace, browser lease и очередью
вызовов. `pix3 mcp` остаётся stdio-входом агента; в режиме workspace он подключается к существующему
серверу, не поднимает второй независимый watcher/relay. Локальный FSA-режим основного плана остаётся
доступен. Нужен общий модуль серверных примитивов, а не две расходящиеся реализации relay.

CLI хранит endpoint и служебную идентичность под `.pix3/`; stdio-клиент проверяет живой процесс,
совпадение корня и серверную сессию, не доверяет одному stale-файлу или `projectId` из манифеста.
Для одного корня допускается один сервер; второй запуск сообщает существующий адрес или конфликт.
Несколько проектов получают отдельные порты и credentials. Одновременные управляющие агенты
не входят в v1: второй получает понятный `busy`.

Режим workspace задаётся явно в конфигурации MCP проекта (предлагаемый флаг
`pix3 mcp --workspace`), чтобы отсутствие `pix3 dev` не переключало клиента молча на FSA-сервер.
Если сервер не запущен, MCP возвращает диагностируемое состояние и пишет в stderr:
«Workspace server is not running. Run pix3 dev in this project directory». Stdout остаётся
только для MCP-протокола. После запуска сервера клиент должен уметь переподключиться без
перезапуска агента; детали retry и status согласовать с жизненным циклом MCP.

### Подключение и доступ

- Сервер слушает loopback; внешний доступ — через пользовательский SSH-проброс.
- Одноразовый секрет достаточной энтропии выдаётся в терминале, имеет срок действия и ограничение
  попыток; обменивается на credential конкретного workspace. Не передаётся в query URL и не
  попадает в обычные логи. Точный формат и срок — решение спайка.
- Все файловые чтения, записи, события и relay требуют аутентификации. Origin/Host allowlist
  дополняют её; отсутствие `Origin` не должно давать неаутентифицированный файловый доступ.
- Для v1 выбирается постоянное сопряжение с отзывом. Браузер хранит случайный credential
  в отдельном хранилище IndexedDB, сервер — его криптографический хеш и метаданные выдачи,
  не исходный credential. Запись «Недавние» содержит ссылку на credential, а не сам секрет.
  Это разделение предотвращает случайную выдачу секрета в списках/логах, но не защищает от XSS
  того же origin. Серверное состояние
  под `.pix3/` исключается из Git и экспорта, с правами только владельца. При копировании проекта
  credential/identity не должны автоматически переносить доверие: смена канонического корня
  инвалидирует сохранённое подключение. `projectId` не идентифицирует физический workspace.
- Отзыв текущего сопряжения доступен в UI при живом соединении; локальное «Забыть» без
  соединения удаляет только браузерный credential и не называется серверным отзывом.
  CLI предоставляет отдельную команду отзыва (окончательный синтаксис определить при реализации),
  которая инвалидирует соответствующие credentials и активные leases. Перезапуск CLI сохраняет
  pairing, но создаёт новый sessionId и сбрасывает разрешение генерации.
- Адрес с другим портом сам по себе не меняет workspace; тот же адрес после замены процесса
  сам по себе не подтверждает его. При несовпадении identity редактор не отправляет отложенные записи.
- Доступ ограничен корнем проекта. Нормализация путей, `..`, абсолютные пути и symlink escape
  проверяются на сервере; в v1 проще запретить операции через symlink. Проверки нужны и для
  создаваемых путей/родителей. Локальные процессы того же пользователя считаются доверенными
  по модели основного плана; это не защита от вредоносного процесса с правом менять сам корень.
- Browser lease на запись и обслуживание агента един; перехват явный. Web Lock помогает только
  внутри одного origin браузера, серверная lease остаётся окончательным арбитром.
- Разрешение генерации с ключами редактора отдельно от доступа к файлам и сбрасывается при
  новой серверной сессии/аренде, как в основном плане.

Опубликованный `https://editor.pix3.dev` обращается к loopback через разрешение Local Network
Access: нужно проверить Chromium/PWA, CORS, mixed-content поведение, long-poll и отказ пользователя
([Chrome: Local Network Access](https://developer.chrome.com/blog/local-network-access)).
Если браузер блокирует соединение, показывается конкретная причина и способ повторить разрешение;
отключение браузерной защиты не является поддерживаемым процессом.

### Backend редактора

Добавляется `workspace` за `ProjectStorageService`; не поддельный `FileSystemDirectoryHandle`.
Потребители должны зависеть от файловых возможностей, а не обязательного browser handle.
Аудит охватывает `ProjectService`, file watch, загрузку сцен и префабов, скриптов, ассетов,
`res://`, импорт/экспорт, восстановление проекта и список недавних.

Подтверждённые точки аудита после внешнего ревью:

- `ProjectService`: открытие, handles и recent descriptors; workspace descriptor содержит backend,
  endpoint, projectId, workspaceId и credential reference.
- `FileWatchService`: `Map<string, FileSystemFileHandle>` и `getFile()` требуют альтернативного
  источника событий. Транспорт пока не зафиксирован: authenticated fetch long-poll/stream проще
  согласовать с заголовком Authorization; нативные EventSource/WebSocket не принимают произвольные
  заголовки тем же способом. Не переносить credential в URL ради выбора SSE/WebSocket.
- `FileSystemAPIService`: остаётся реализацией FSA, не становится HTTP-клиентом. Диспетчеризация
  storage/capabilities принадлежит `ProjectStorageService`; интерфейс backend уточняется аудитом.
- `SaveSceneOperation`: fallback `storage.getLastModified(filePath)` **уже есть**, поэтому это
  не доказанный блокер. Проверить отсутствие handle в workspace, подавление собственного watch
  события и использование хешей там, где timestamp недостаточен.
- `src/services/assets/ResourceManager.ts`: редактор уже читает проектные ресурсы через storage.
  Проверить его fallback на public URL: ошибка соединения workspace не должна маскироваться
  под загрузку одноимённого ресурса из другого источника.
- `ThumbnailGenerator`: прямое чтение через файловый сервис требует проверки и перевода на
  storage для workspace. Эти точки не составляют исчерпывающий список зависимостей.

`src/sw.ts` во внешнем ревью назван главным блокером, но `vite.config.ts` явно указывает,
что этот legacy worker не зарегистрирован; PWA использует `generateSW`. Переписывать его
в workspace-proxy не требуется. Проверять нужно действующий путь ResourceManager → storage
и кеширование реально сгенерированного PWA worker. Любой последующий SW-proxy потребует отдельного
обоснования и изоляции ресурсов разных workspace/вкладок, а не глобального «текущего проекта».

Все пути файлового протокола — относительные от корня, с POSIX-разделителем `/`, независимо от
ОС клиента и сервера. Сервер отклоняет абсолютные, drive/UNC-пути, обратные слэши и обход корня;
правила percent-decoding едины и не допускают повторного декодирования. Регистр имени сохраняется;
коллизии и чувствительность к регистру определяются серверной файловой системой.

Для открытия и сверки нужен пакетный manifest: пути, типы, размеры, mtime и хеши файлов в
объявленной области сканирования, плюс session/revision. Не хешировать `node_modules`, `.git`
и весь корень вслепую; область игровой ревизии берётся из §5 D основного плана, листинг прочих
доступных файлов — отдельная возможность. Большой manifest допускает страницы, но изменение
ревизии между ними должно быть обнаружено. Вычисление хешей кешируется; барьер сохраняет
требования проверки содержимого. Ответы ресурсов используют ETag по хешу фактически отданных
байтов; кеш разделён по workspace и пути/версии. Ограниченный параллелизм чтения и пакетные
метаданные исключают последовательный stat на каждый ассет. Manifest не является атомарным
снимком произвольно изменяемой папки.

Минимальный API: directory listing/stat, текстовое и бинарное чтение, запись, создание каталога,
удаление, перемещение, сверка хешей и поток событий. Ресурсы с авторизацией загружаются через
адаптер и передаются загрузчикам подходящим способом (например Blob URL с корректным dispose),
а не получают долгоживущий секрет в URL. Видео/аудио и крупные файлы требуют отдельной проверки
streaming/range и памяти: нельзя считать чтение маленькой сцены достаточным прототипом.

Изменения документа по-прежнему идут через CommandDispatcher → Operation. Backend исполняет
файловые операции, не даёт UI нового обходного пути мутаций. Состояние соединения принадлежит сервису.

## 6. Согласование записей и восстановление соединения

Применяются правила merge/protected set/recovery из §4.3 основного плана. Watcher на сервере
доставляет события с номером последовательности и server session; пропуск событий, reconnect
или перезапуск требуют повторного сканирования. Запись временного невалидного YAML агентом
не уничтожает последнюю валидную сцену. События не содержат обещания «увидели каждую запись».

Запись из редактора несёт base hash и mutation id. Сервер сериализует собственные записи,
проверяет ожидаемую базу и публикует результат. Несовпадение запускает согласование, а не
безусловную перезапись. Повтор после потери HTTP-ответа не должен повторно применять rename/delete:
в пределах серверной сессии нужен журнал результатов mutation id. После потери журнала/перезапуска
статус считается неопределённым и проверяется по фактическому состоянию, не слепым retry.

**Ограничение:** base hash + atomic rename не обеспечивают CAS относительно произвольной записи
Claude Code напрямую в файловую систему. Между проверкой и заменой остаётся гонка основного
плана. Не обещаем её устранения; сохраняем обнаруженные версии и сверки ожиданий агента.
Устранение потребовало бы кооперации всех писателей или другого контракта записи.

При обрыве:

- UI явно показывает недоступность сервера; не отмечает изменения сохранёнными до подтверждения.
- Несохранённые правки сохраняются в памяти. Допускается продолжать редактирование загруженного
  документа, но нет обещания полноценной offline-работы; закрытие страницы с такими правками
  требует предупреждения. Recovery-копия в браузере допустима, не становится вторым рабочим checkout.
- Новый Play/проверка блокируется понятной ошибкой соединения. Уже запущенная игра может продолжать
  работать из загруженных данных, но не считается подтверждённым прогоном; новые ресурсы могут не загрузиться.
- После reconnect сначала проверяются identity, lease и состояние диска, затем согласуются правки.
  Отложенные записи никогда не сбрасываются поверх изменившегося сервера автоматически.
- Прерванный MCP-вызов возвращает ошибку/неопределённый исход, не выдуманный успех. Повтор действий
  с побочным эффектом требует выяснить состояние; новая lease не исполняет старую очередь вслепую.

## 7. Объём первой версии и этапы

В v1: один пользователь, один серверный корень, один редактор-владелец, один управляющий агент;
Chromium на desktop, опубликованный редактор/PWA, SSH port forwarding средствами пользователя;
файлы, ручное редактирование, Play и MCP-цикл. Отсутствие FSA снимает одну браузерную зависимость,
но поддержка Firefox/Safari не объявляется без отдельной проверки всего редактора.

За пределами v1: SSH-клиент внутри Pix3, VS Code extension, автоматическое управление Chrome,
headless/CI-плеер, удалённый рендеринг, cloud/collab backend, несколько одновременно пишущих
редакторов, гарантированный immutable snapshot прогона, полноценный offline-sync и обязательная
отладка из VS Code. Отдельный player URL может появиться позже, для данного процесса не нужен.

1. **Спайк транспорта и ресурсов.** Реальный Remote SSH, опубликованный origin и PWA; вход с секретом,
   чтение/запись тестового проекта, загрузка скрипта и нескольких типов бинарных ассетов,
   обрыв/восстановление. Проверить LNA и независимость от выбранного локального порта.
2. **Backend и жизненный цикл.** Аудит FSA-зависимостей, storage API, ресурсы, lease, недавние,
   серверные события, согласование записей, отказ/восстановление. Использует результаты фазы 2
   основного плана, не реализует отдельный merge.
3. **MCP и проверяемый Play.** Подключение stdio к живому серверу, общий relay и барьер фазы 3,
   ошибки, скриншоты, source maps, отзыв разрешений. Сервер работает и без агента.
4. **Приёмка пользовательского цикла.** Матрица ниже и короткая инструкция в канонических docs.
   Обновить основной план и его метрики с учётом дополнительного пути подключения.

Размер работы предварительно M/L; календарную оценку дать после аудита прямых FSA-зависимостей
и спайка бинарных ресурсов. Это отдельный пакет работ, не бесплатная опция существующего relay.

## 8. Критерии приёмки

Проверяется реальная удалённая папка и локальный Chrome, а не два процесса с общим локальным
каталогом. Пользовательские действия проверяются в работающем редакторе через DevTools MCP,
состояние и независимые измерения; screenshot — для визуальных вопросов.

| Проверка | Ожидаемое свидетельство |
| --- | --- |
| Подключение без локальной папки | Ни одного FSA-пикера; редактор читает серверный проект через проброшенный порт |
| Разные номера портов | Подключение через заданный локальный endpoint работает без сканирования удалённого диапазона |
| Ручная правка | Координата изменена в UI; независимое чтение YAML на сервере подтверждает сохранение |
| Правка агентом и немедленный Play | Скрипт/сцена с уникальным маркером версии; наблюдаемое поведение и хеши подтверждают новую версию |
| Смена ассета без смены имени | Независимо заданное новое изображение видно в игре; кеш не оставляет старую текстуру |
| Полнота ресурсов | Префаб, импорт скрипта, локализация, модель, текстура, аудио/видео загружаются через backend |
| Создание/удаление/rename | Дерево ресурсов и ошибки ссылок соответствуют серверному диску |
| Одновременные правки | Ручная и агентская правки проходят таблицу merge основного плана; конфликт не замалчивается |
| Потеря ответа на запись | Повтор mutation id не дублирует операцию; редактор выясняет результат |
| Разрыв SSH с dirty-сценой | Нет ложного «сохранено»; после reconnect сначала сверка и merge |
| Остановка Claude Code | Редактор продолжает читать и сохранять через `pix3 dev` |
| Замена проекта на том же порту | Старое подключение не применяет накопленные записи к другому корню |
| Вторая вкладка / второй агент | Сервер обеспечивает lease/busy; перехват вкладки явный |
| Watcher пропустил событие | Барьер обнаруживает расхождение полным сканированием |
| Отладка скрипта | Ошибка указывает исходный TS и строку; breakpoint в Chrome срабатывает и после перекомпиляции |
| Доступ без credential / выход из корня | Чтение и запись отклоняются, включая бинарные маршруты и symlink |
| Отказ LNA / несовместимый протокол | Конкретное объяснение в UI, без бесконечного «подключаемся» |

Измерить отдельно первый вход, повторный вход, save-to-disk и edit-to-verified-play; записать RTT,
размер проекта, cold/warm cache и долю времени загрузки ресурсов. При RTT около 100 мс проверить,
что обход проекта не превращается в сотни последовательных запросов. Численные SLA утвердить
после спайка; локальные замеры основного плана не выдавать за результаты SSH.

Для испытаний использовать временный проект вне `samples/`; после очистки убедиться, что
`git status --short -- samples/` пуст. При исходно непустом статусе сохранить пользовательские
изменения и отдельно подтвердить отсутствие собственных изменений в samples.

## 9. Вопросы для ревью

1. Принимаем ли workspace backend как обязательный путь Remote SSH, сохраняя FSA для локального входа?
2. Достаточен ли UX «одна команда + один проброшенный порт + подключение из PWA», без VS Code extension?
3. Достаточна ли выбранная модель постоянного сопряжения, хранения хеша на сервере и отзыва (§5)?
4. Достаточны ли ограничения гонок и прогонов основного плана для удалённого пути, или immutable snapshot
   требуется раньше фазы 4? Это меняет объём работы, а не только транспорт.
5. Какие существующие функции редактора требуют настоящих handles и должны быть переведены на
   capability-интерфейс до заявления о полноценном редактировании удалённого проекта?


## 10. Разбор внешнего ревью (ревизия 2)

Приняты: постоянное pairing с отзывом, пакетные метаданные и hash-based ETag, явный workspace-режим
stdio-клиента с диагностикой отсутствующего сервера, POSIX-пути протокола и встроенные исходники
source maps. Требование source maps формулируется по результату (`sourcesContent` содержит TS),
а не как непроверенное имя опции esbuild. Исходный объём v1 и ограничения прогонов сохранены.

Исправлены выводы аудита: legacy `src/sw.ts` не зарегистрирован; у `SaveSceneOperation` уже есть
fallback без handle. Добавлены действующий ResourceManager и прямой файловый доступ thumbnails.
Постоянный секрет не помещается непосредственно в recent descriptor.

Не приняты как доказанные утверждения: «LNA/CORS переиспользуются на 100%» (нужен спайк реального
transport/resource path), «каждый обрыв SSH требует нового pairing» (краткий обрыв и перезапуск
процесса различаются), «snapshot обязательно копирует весь проект» (возможны и иные реализации).
Отсрочка immutable snapshot — решение о гарантиях и объёме v1, а не доказанная невозможность
эффективного снимка. Положительное внешнее ревью не заменяет проверку критериев приёмки.
