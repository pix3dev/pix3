# Strophe Public API — что нужно Pix3

Спецификация-запрос от команды Pix3 (pix3.dev) к команде Strophe (strophe.app).
Версия 1.0 — 2026-08-01. Здесь описан контракт, который мы готовы потреблять «как есть», с
обоснованиями из нашего реального опыта интеграции других провайдеров.

> **Статус на 2026-08-11: разблокировано, документ стал историческим базисом.** Strophe выпустили
> API (`https://strophe.app/api/v1`) во многом по этой спеке. Что подтвердилось живыми запросами,
> чего в их API нет и что мы просим доделать — в
> [strophe-integration-feedback.md](strophe-integration-feedback.md) (это же документ для передачи
> их менеджеру). Ниже — исходный текст запроса без правок: он остаётся системой координат, по
> которой мы сравниваем реализацию.

## 0. Резюме

**Что мы просим одним абзацем.** Pix3 — браузерный редактор 2D/3D-сцен, работающий целиком
на клиенте, со встроенным AI-агентом, который автономно генерирует ассеты. Мы хотим, чтобы
пользователь Pix3 нажал «Connect Strophe» один раз, а дальше редактор и агент через ваш API
генерировали изображения, 3D-модели, видео, звук и вызывали LLM — оплачивая всё вашими
кредитами, без единого API-ключа сторонних провайдеров на нашей стороне. Для этого нужен:
браузеро-безопасная аутентификация (OAuth-подобный connect + короткоживущие scoped-токены),
единая асинхронная job-модель с прогрессом и отменой, discovery-каталог моделей/пайплайнов с
ценами в кредитах, и биллинг как часть API (баланс, оценка до запуска, факт в ответе,
идемпотентность). Ваши нодовые пайплайны, опубликованные как типизированные эндпоинты, — это
то, что для нас ценнее любых сырых моделей.

**Три главных требования (без них интеграция невозможна):**

1. **CORS везде, включая CDN с результатами.** Каждый эндпоинт API и каждый URL с артефактом
   должен отдаваться с корректными CORS-заголовками. Мы уже обожглись: Tripo3D отдаёт
   presigned URL на GLB без `Access-Control-Allow-Origin` — браузер не может его скачать, и
   нам пришлось строить SSRF-защищённый серверный прокси только ради скачивания. Один
   недостающий заголовок обесценивает весь остальной API для браузерного клиента.
2. **Токены, которые не страшно держать в браузере.** Долгоживущий API-ключ в клиентском
   приложении — это утечка by design. Нужны: connect-флоу (device code или PKCE),
   короткоживущие access-токены, scopes, лимит трат на токен, отзыв.
3. **Биллинг — первоклассная часть контракта.** Баланс, `quote` до запуска, фактическая
   стоимость в каждом ответе, `Idempotency-Key` (ретрай не списывает дважды), отдельный
   машиночитаемый код «недостаточно кредитов». Наш агент запускает генерации пачками без
   человека в цикле — без этих механизмов мы не можем дать ему доступ к чужим деньгам.

## 1. Контекст потребителя: как Pix3 будет вызывать API

Чтобы требования не выглядели произвольными — что у нас уже есть и с чем API стыкуется:

- **Всё выполняется в браузере.** Pix3 — клиентское приложение (File System Access API),
  серверная часть опциональна. Значит: только CORS-совместимые вызовы, никаких вебхуков
  (браузеру некуда их принимать), секреты хранить негде, кроме браузерного хранилища.
- **Провайдерная абстракция изображений** уже существует (Gemini, OpenAI Image): параметры
  `prompt / references[] / aspectRatio / imageSize / quality / background / outputMimeType /
  count / AbortSignal`, на каждую модель — декларация capabilities, типизированные ошибки.
  Strophe станет ещё одним провайдером в этом реестре — чем ближе ваш контракт к этой форме,
  тем меньше адаптера.
- **LLM-абстракция** уже существует (Anthropic, Gemini, OpenAI-compatible, и др.): tools с
  JSON Schema, streaming, usage с разбивкой кэша, живой каталог моделей. Если вы дадите
  OpenAI-совместимый endpoint — мы подключаем вас практически нулевым кодом.
- **3D** уже интегрирован через Tripo (upload → task → поллинг → GLB) — мы знаем все грабли
  этой схемы и перечислим их ниже.
- **In-editor AI-агент** вызывает генерацию как инструмент: автономно, параллельно, с
  ретраями. Отсюда требования к идемпотентности, оценке стоимости и лимитам.
- **История генераций**: каждый сгенерированный ассет сохраняется в проект с метаданными
  происхождения — нам нужны модель, seed, промпт и стоимость в ответе.

## 2. Базовые соглашения

### 2.1 Транспорт и версионирование

- Base URL: `https://api.strophe.app/v1/` (или любой ваш — важно, что версия в пути).
- JSON везде, UTF-8. Бинарные входы — через `/v1/files` (см. §6), бинарные выходы — через
  CDN-URL в артефактах (см. §5).
- Мажорная версия в пути (`/v1`). Ломающие изменения → `/v2`, `/v1` живёт минимум 12 месяцев
  после анонса. Аддитивные изменения (новые поля, новые модели) — без смены версии; мы
  обязуемся игнорировать неизвестные поля.
- `GET /v1/catalog` возвращает `api_version` (дата ревизии, например `"2026-08-01"`), чтобы
  клиент мог детектировать новые возможности.

### 2.2 CORS — точный список требований

Для **каждого** эндпоинта API (включая OAuth-эндпоинты и SSE):

```
Access-Control-Allow-Origin: <echo Origin запроса или *>
Access-Control-Allow-Methods: GET, POST, DELETE, OPTIONS
Access-Control-Allow-Headers: Authorization, Content-Type, Idempotency-Key, X-Strophe-Client
Access-Control-Expose-Headers: Retry-After, X-Request-Id, X-Credits-Charged
Access-Control-Max-Age: 86400
```

Preflight `OPTIONS` должен отвечать `204` без аутентификации.

Для **CDN-выдачи артефактов** (критично, это боль Tripo):

```
Access-Control-Allow-Origin: *
```

Артефакты доступны по capability-URL (секрет в самом URL), поэтому `*` здесь безопасен и
правилен: без него `fetch()` из браузера не может прочитать тело ответа, и весь API
становится непригодным для клиентских приложений. Пожалуйста, проверьте это на реальном
`fetch()` из чужого origin до релиза — это ошибка номер один у generic-платформ.

### 2.3 Идемпотентность

Все `POST`, создающие job или списывающие кредиты, принимают заголовок:

```
Idempotency-Key: <uuid, генерирует клиент>
```

Семантика: повторный запрос с тем же ключом в окне ≥ 24 ч возвращает **тот же** job (тот же
`job_id`, без нового списания). Конфликт (тот же ключ, другое тело) → `409` с кодом
`idempotency_conflict`. Это не опция: наш агент ретраит по сетевым таймаутам, и без
идемпотентности каждый ретрай — двойное списание и дубликат генерации.

### 2.4 Служебные заголовки

- `X-Request-Id` в каждом ответе — для разбора инцидентов.
- `Retry-After` (секунды) при `429` и `503` — наш клиент его честно уважает.

## 3. Аутентификация из браузера

### 3.1 Почему не API-ключ

Pix3 не имеет обязательного сервера: ключ, выданный пользователю, жил бы в браузерном
хранилище и уходил бы в каждый запрос из подконтрольной пользователю среды. Утечка ключа =
утечка всего баланса без ограничений. Ровно из-за этого для провайдеров без браузерной
модели токенов мы были вынуждены построить отдельный локальный процесс
(credential-injecting proxy), который держит ключи на диске пользователя и никогда не отдаёт
их странице. Если ваш API сразу спроектирован под браузер — вся эта конструкция не нужна, и
интеграция сокращается на порядок.

### 3.2 Что просим

OAuth 2.0, два грант-флоу (достаточно любого одного, лучше оба):

- **Authorization Code + PKCE** (RFC 7636) — для хостнутого редактора с фиксированным
  origin: редирект на `https://strophe.app/oauth/authorize`, согласие, редирект обратно.
- **Device Authorization Grant** (RFC 8628) — универсальный запасной: работает с localhost,
  dev-сборками и любым origin без регистрации redirect URI. Для нас предпочтителен как
  минимум на старте.

Токены:

- **Access token**: короткоживущий (30–60 мин), Bearer, привязан к scopes.
- **Refresh token**: долгоживущий, с ротацией при каждом refresh (`refresh_token` одноразовый,
  выдаётся новый). Хранится у нас в SecretStorage редактора.
- `POST /oauth/token` и `POST /oauth/revoke` (RFC 7009) — с CORS (см. §2.2), потому что их
  вызывает браузер напрямую.

Scopes (предлагаемый набор):

```
generate:image  generate:model3d  generate:video  generate:audio
llm:chat  files:write  billing:read  catalog:read
```

**Лимиты трат на грант** — задаются на экране согласия и/или в кабинете Strophe:

```json
{ "max_credits_per_day": 500, "max_credits_per_job": 50 }
```

Превышение → `403` с кодом `spend_limit_exceeded` (не `402`! баланс может быть положительным).
Это то, что позволяет пользователю дать автономному агенту «карманные деньги», а не кошелёк.

Отзыв: revoke-эндпоинт + страница в кабинете Strophe «подключённые приложения» со списком
грантов и кнопкой отключения.

### 3.3 Сценарий «Connect» end-to-end (как мы его реализуем)

1. Пользователь в настройках Pix3 нажимает **Connect Strophe account**.
2. Pix3 вызывает `POST /oauth/device/code` c `client_id` и scopes → получает
   `{device_code, user_code, verification_uri, interval}`.
3. Редактор открывает `verification_uri` в новой вкладке и показывает `user_code`.
4. Пользователь логинится на strophe.app, подтверждает scopes и (опционально) выставляет
   дневной лимит кредитов для Pix3.
5. Pix3 поллит `POST /oauth/token` (grant_type `device_code`) с интервалом `interval` →
   получает `{access_token, refresh_token, expires_in, scope}`.
6. Refresh token — в SecretStorage; access token — в памяти вкладки. Далее каждый запрос
   идёт с `Authorization: Bearer <access_token>`, по `401 token_expired` — тихий refresh.
7. Сразу после подключения Pix3 вызывает `GET /v1/catalog` и `GET /v1/billing/balance` —
   пикеры моделей и индикатор кредитов заполняются без дополнительной настройки.

Вопрос к вам: если полноценный OAuth в v1 не успевается, минимально приемлемый для нас
компромисс — «browser key»: токен, создаваемый в кабинете, у которого **обязательны** срок
жизни, scopes и лимит трат, и который сервер отличает от полного API-ключа. Но это именно
компромисс: правильная цель — connect-флоу.

## 4. Единая job-модель

### 4.1 Принцип

Одна форма для всех тяжёлых задач (image, 3D, video, audio, pipeline). LLM — отдельная лана
(§9), она не job. Job создаётся одним `POST`, дальше — поллинг или SSE.

```
POST   /v1/jobs                  создать job
GET    /v1/jobs/{id}             статус + результат
GET    /v1/jobs/{id}/events      SSE-поток прогресса
POST   /v1/jobs/{id}/cancel      отмена
GET    /v1/jobs?limit=&cursor=   история (для нашей Generation History)
```

### 4.2 Создание

```json
POST /v1/jobs
Authorization: Bearer <token>
Idempotency-Key: 7c9e6679-7425-40de-944b-e07fc1f90ae7
Prefer: wait=20

{
  "type": "image.generate",
  "model": "img/flux-pro-1.1",
  "input": {
    "prompt": "isometric wooden crate, game asset, clean silhouette",
    "reference_files": ["file_9f2c1"],
    "aspect_ratio": "1:1",
    "size": "1K",
    "quality": "high",
    "background": "transparent",
    "output_mime": "image/png",
    "count": 2,
    "seed": 1234567
  },
  "metadata": { "pix3_project": "sky-defender", "tool_call": "generate_asset#41" }
}
```

- `type` — дискриминатор: `image.generate`, `model3d.generate`, `video.generate`,
  `audio.sfx`, `audio.music`, `audio.tts`, `pipeline.run`.
- `metadata` — до 2 КБ произвольного JSON от клиента, возвращается в job как есть (нам нужно
  связывать job с вызовом инструмента агента).
- **`Prefer: wait=<сек>`** — гибрид sync/async: если job завершился за N секунд, сервер сразу
  отвечает `200` с готовым job (`status: "succeeded"`); иначе `202` с job в статусе
  `queued`/`running`, и клиент переходит к поллингу/SSE. Быстрые image-модели чаще всего
  уложатся, и клиенту не нужно два запроса. Если гибрид сложен — ок и чистый async
  (`202` всегда), но тогда SSE обязателен.

### 4.3 Объект job

```json
{
  "id": "job_01j9x7v3",
  "type": "image.generate",
  "model": "img/flux-pro-1.1",
  "status": "succeeded",
  "progress": 100,
  "created_at": "2026-08-01T10:20:31Z",
  "finished_at": "2026-08-01T10:20:44Z",
  "cost": { "quoted_credits": 8, "charged_credits": 8 },
  "input_digest": { "prompt": "isometric wooden crate…", "seed": 1234567 },
  "artifacts": [
    {
      "id": "art_5501",
      "role": "image",
      "mime": "image/png",
      "width": 1024,
      "height": 1024,
      "size_bytes": 412873,
      "url": "https://cdn.strophe.app/a/art_5501?sig=…",
      "url_expires_at": "2026-08-02T10:20:44Z",
      "seed": 1234567
    },
    { "id": "art_5502", "role": "image", "mime": "image/png", "width": 1024, "height": 1024,
      "size_bytes": 398112, "url": "https://cdn.strophe.app/a/art_5502?sig=…",
      "url_expires_at": "2026-08-02T10:20:44Z", "seed": 1234568 }
  ],
  "error": null,
  "metadata": { "pix3_project": "sky-defender", "tool_call": "generate_asset#41" }
}
```

Статусы: `queued → running → succeeded | failed | cancelled`. Плюс `progress` 0–100 (может
быть грубым; для 3D/video он критичен, пользователь смотрит на прогресс-бар минуты).
`failed` обязан нести `error` (см. §11) — job без артефактов и без ошибки для нас нечитаем
(у Tripo это отдельная категория боли: «success» с пустым output).

### 4.4 Уведомление о завершении: поллинг и SSE, не вебхуки

Прямо фиксируем: **вебхуки браузерному клиенту недоступны** — нам некуда их принимать.
Поэтому:

- **Поллинг** `GET /v1/jobs/{id}` — базовый механизм, должен быть дёшев (не считается в
  rate limit генераций или считается отдельным щедрым лимитом). Рекомендуемый интервал
  сообщайте в ответе: `"poll_interval_ms": 2000`.
- **SSE** `GET /v1/jobs/{id}/events` (`Content-Type: text/event-stream`) — предпочтительный
  механизм: события `progress`, `succeeded`, `failed`, `cancelled`, данные — тот же объект
  job (можно сокращённый). Важно: мы читаем SSE через `fetch()` со стримингом, а не через
  `EventSource`, поэтому `Authorization`-заголовок нам доступен — **не** нужно изобретать
  токен в query string. Нужен только CORS на этом эндпоинте.
- Вебхуки можете добавить для серверных потребителей — нам они не мешают, но не проектируйте
  API так, что без вебхука нельзя жить.

### 4.5 Отмена

`POST /v1/jobs/{id}/cancel` → job переходит в `cancelled` (или остаётся `succeeded`, если уже
доехал — тогда ответ это честно показывает). Требование к биллингу: отменённый до старта job
не списывает ничего; отменённый в процессе — списывает не больше фактически потреблённого, и
`cost.charged_credits` в финальном объекте job отражает факт. Наш агент активно отменяет
задачи (пользователь передумал, таймаут инструмента) — «отмена без прекращения списания»
сделает функцию бесполезной.

## 5. Формат результата: артефакты

Один job → массив артефактов. Это принципиально: реальные задачи мультиартефактны
(GLB + текстуры; спрайт-лист + JSON-атлас; аудио + метаданные лупа; набор из N картинок).

Поля артефакта: `id`, `role`, `mime`, `url`, `url_expires_at`, `size_bytes`, плюс
модальность-специфичные: `width/height` (image/video), `duration_ms` (audio/video),
`seed`, `loop_start_ms/loop_end_ms` (audio), произвольный `meta` (JSON).

**Роли** — строковый enum, объявляемый в каталоге на модель/пайплайн, например:
`image`, `image.mask`, `spritesheet`, `atlas.json`, `model.glb`, `texture.albedo`,
`texture.normal`, `texture.roughness`, `texture.ao`, `video`, `audio`, `captions`.
Клиент по роли понимает, что куда класть, не парся имена файлов.

**Inline vs URL:**

- По умолчанию — **URL на CDN** (с CORS, §2.2). Presigned/capability — как вам удобно.
- **Срок жизни URL ≥ 24 часа** и эндпоинт переполучения:
  `GET /v1/jobs/{id}` возвращает свежие URL при каждом обращении (т.е. подпись генерируется
  на чтение, а не одна навсегда). Артефакты хранятся у вас ≥ 7 дней.
- Опция `"response_format": "inline"` в input для мелочи (< ~1 МБ): артефакт приходит как
  `"data": "<base64>"` без `data:`-префикса, поле `url` отсутствует. Наш image-пайплайн
  исторически работает на base64 — это избавит от лишнего roundtrip за маленькими PNG.

**Запасной путь, если CORS на CDN не выходит.** Бывает, что CDN/объектное хранилище не под
вашим контролем (как у Tripo). Тогда нужен эндпоинт скачивания с вашего API-origin, где CORS
у вас точно есть:

```
GET /v1/artifacts/{id}/content
→ 302 на CDN  (не поможет: редирект на origin без CORS браузер не прочитает)
→ 200 + тело   ← вот это нам и нужно: стриминг с вашего origin, с CORS-заголовками
```

Это дороже для вас по трафику, поэтому правильный путь — всё-таки CORS на CDN, а этот
эндпоинт — страховка. Но без одного из двух браузерный клиент не может забрать результат.

## 6. Загрузка входных данных: `/v1/files`

Агент шлёт один и тот же референс (стиль проекта, скрин сцены) десятки раз — гонять по 4 МБ
base64 в каждом запросе дорого и медленно. Просим переиспользуемые файлы:

```json
POST /v1/files            (multipart/form-data: file=<binary>; или raw body + Content-Type)
→ 201
{
  "id": "file_9f2c1",
  "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "mime": "image/png",
  "size_bytes": 4183921,
  "expires_at": "2026-08-31T00:00:00Z"
}
```

- **Дедупликация по sha256**: повторная загрузка того же содержимого возвращает существующий
  `id` (идеально — ещё и `GET /v1/files/by-sha256/{hash}`, чтобы вообще не загружать).
- TTL ≥ 30 дней, продлевается при использовании файла в job.
- `file_id` принимается везде, где на вход идёт изображение/аудио/модель:
  `reference_files`, `input_image`, `style_ref` и т.д. Inline base64 как альтернатива для
  разовых мелких входов тоже нужен (поле `reference_images: [{mime, data}]`).
- Лимит размера объявите в каталоге (`limits.max_file_bytes`).

      "kind": "llm",

      "capabilities": {
        "tools": true, "vision": true, "streaming": true,
        "context_window": 200000, "max_output_tokens": 16384,

    {
      "id": "strph/sprite-with-alpha",
      "version": 3,

      "pricing": { "unit": "run", "credits": 7 },

        "required": ["prompt"],
        "properties": {
          "prompt": { "type": "string" },

          "target_size": { "type": "integer", "minimum": 64, "maximum": 2048 }

Требования по сути:

- Каталог живой: модели появляются/исчезают — мы перечитываем каталог на старте сессии и по
  кнопке Refresh, как уже делаем для LLM-провайдеров.

## 8. Модальности: параметры input по типам job

### 8.1 `image.generate`

Поля `input` (маппинг на наш существующий контракт, ничего экзотического):

| Поле | Тип | Прим. |
|---|---|---|
| `prompt` | string | обязательное |
| `reference_files` | string[] | file id (§6) |
| `reference_images` | {mime,data}[] | inline-альтернатива |
| `aspect_ratio` | `"1:1"\|"3:4"\|"4:3"\|"16:9"\|"9:16"` | отсутствие поля = авто |
| `size` | string из каталога (`"1K"…`) | |
| `quality` | string из каталога | |
| `background` | `"auto"\|"transparent"\|"opaque"` | `transparent` ⇒ настоящий альфа-канал в PNG |
| `output_mime` | `image/png\|image/jpeg\|image/webp` | |
| `count` | int ≤ maxCount | N артефактов в одном job |
| `seed` | int | см. §12 |

Про `transparent`: если модель не умеет — честный отказ валидацией (`422 invalid_input`),
а не тихое игнорирование: у нас на этом флаге завязано, гонять ли локальный bg-removal.
Если у вас есть нода удаления фона — прозрачность через пайплайн (§9 каталога) нам даже
интереснее, чем нативная поддержка моделью.

### 8.2 `model3d.generate`

Схема async job покрывает всё, что мы делаем с Tripo, но просим не повторять их ошибки:

```json
"input": {
  "input_image": "file_9f2c1",
  "output_format": "glb",
  "pbr": true,
  "polycount_budget": 15000,
  "texture_size": 1024
}
```

- Выход — **GLB одним артефактом** (`role: "model.glb"`, текстуры упакованы внутрь) — это
  наш основной путь; отдельные PBR-текстуры как дополнительные артефакты
  (`texture.albedo/normal/roughness/ao`) — приветствуются опционально.
- **CDN-URL с CORS** — см. §2.2; это дословно та грабля, из-за которой у нас существует
  серверный прокси для Tripo.
- **`progress` обязателен**: генерация идёт минуты, пустой прогресс-бар — плохой UX.
- `failed` со структурированной ошибкой, включая модерацию входного изображения
  (`moderation_blocked`), а не просто статус `banned` без пояснений (ещё одна грабля Tripo).
- `polycount_budget` — важно для нас: движок целится в WebGL/мобильный HTML5, бюджет
  полигонов — не пожелание, а требование производительности.

### 8.3 `video.generate`

Только async. `input`: `prompt`, `input_image`/`reference_files`, `duration_s`, `fps`,
`resolution` (`"720p"|"1080p"`), `output_mime` (`video/mp4|video/webm`), `seed`.
Артефакты: `role: "video"` + опционально `role: "image"` (постер-кадр). Для нас видео —
последняя из модальностей по приоритету (см. §16), но контракт пусть будет той же формы.

### 8.4 Аудио: `audio.sfx`, `audio.music`, `audio.tts`

У Pix3 аудио-генерации сегодня нет вообще — чистое поле, берём любой разумный контракт этой
формы:

```json
{ "type": "audio.sfx",
  "input": { "prompt": "short UI click, wooden, dry", "duration_ms": 400, "output_mime": "audio/wav" } }

{ "type": "audio.music",
  "input": { "prompt": "calm exploration loop, 8-bit chiptune", "duration_ms": 30000,
             "loop": true, "output_mime": "audio/ogg" } }

{ "type": "audio.tts",
  "input": { "text": "Нажмите, чтобы начать", "locale": "ru-RU", "voice": "voice_id_из_каталога",
             "output_mime": "audio/ogg" } }
```

Специфика, которая важна движку:

- **`loop: true` у музыки** ⇒ либо бесшовный луп by construction, либо честные
  `loop_start_ms/loop_end_ms` в метаданных артефакта — иначе музыка в игре щёлкает на стыке.
- **TTS с явной `locale`**: у Pix3 есть система локализации (строки и спрайты по локалям);
  сценарий «одна реплика × N локалей» — реальный. Батч-вариант (массив
  `{text, locale}` → массив артефактов с `meta.locale`) — nice-to-have.
- Каталог голосов TTS — внутри capabilities модели (`voices: [{id, label, locales[]}]`).

## 9. LLM-лана: OpenAI-совместимый endpoint

Самый дешёвый путь для обеих сторон. У нас уже есть работающий OpenAI-compatible провайдер —
если вы поднимаете совместимый endpoint, Pix3 подключает LLM Strophe практически нулевым
кодом: пользователь получает вашу модель в пикере агента в день релиза вашего API.

### 9.1 Минимальный контракт

- `POST /v1/chat/completions` — OpenAI Chat Completions API, с CORS, auth тем же Bearer.
- `GET /v1/models` — живой список моделей (мы оверлеим его поверх статического каталога).
- Обязательные возможности:
  - **tools / function calling** (`tools: [{type:"function", function:{name, description,
    parameters: <JSON Schema>}}]`, `tool_calls` в ответе, `role:"tool"` в истории) — весь наш
    агент построен на инструментах, LLM без tools для нас бесполезен;
  - **streaming** (SSE `stream: true`) + `stream_options: {"include_usage": true}` — usage в
    финальном чанке;
  - **`usage` с разбивкой кэша**: `prompt_tokens`, `completion_tokens`,
    `prompt_tokens_details.cached_tokens` — наш UI показывает контекст-бар с кэшированным
    сегментом и считает стоимость шага агента;
  - **`reasoning_effort`** (`"low"|"medium"|"high"`) для моделей, у которых есть ручка
    глубины размышления; допустимые уровни — в capabilities каталога;
  - vision-вход (`image_url` с `data:`-URI) — агент показывает модели скриншоты сцены.
- Кредиты: фактическое списание за вызов — в расширении ответа
  (`"usage": { …, "credits_charged": 0.42 }`) и/или заголовке `X-Credits-Charged`. Цена за
  1M токенов (вход/выход/кэш-чтение) — в каталоге (§7), чтобы пикер показывал стоимость.

### 9.2 Опционально: Anthropic-совместимый `/v1/messages`

Если под капотом у вас есть Anthropic-модели — их лучше отдавать через совместимый
`/v1/messages` (у нас есть и такой провайдер): тогда работают нативные `cache_control`
брейкпойнты prompt caching, что для многошагового агента снижает стоимость в разы. Не
обязательно для v1, но заложите в архитектуру: «совместимый passthrough-формат» масштабируется
лучше, чем «всё через одну собственную схему».

### 9.3 Явное анти-требование

Пожалуйста, **не** изобретайте собственный несовместимый chat-формат. Любое отклонение от
OpenAI-совместимости (другие имена полей, другой стриминг) превращает «нулевой код» в
«недели адаптера» — и так у каждого вашего потребителя.

## 10. Биллинг как часть API

### 10.1 Баланс

```json
GET /v1/billing/balance
→ 200
{ "credits": 1234.5, "plan": "pro", "renews_at": "2026-08-15T00:00:00Z" }
```

Показ баланса прямо в редакторе — обязательная часть UX «плачу Strophe, ключей нет».

### 10.2 Оценка до запуска (quote)

```json
POST /v1/quote
{ "type": "image.generate", "model": "img/flux-pro-1.1",
  "input": { "prompt": "…", "size": "2K", "quality": "high", "count": 4 } }
→ 200
{ "credits": 48, "breakdown": [ { "item": "image 2K high", "unit_credits": 12, "count": 4 } ] }
```

Без побочных эффектов и без списания. Зачем: агент перед пачкой генераций считает бюджет и
спрашивает подтверждение у пользователя, если выходит за порог. Для LLM quote не нужен
(стоимость токен-зависима) — там достаточно цен в каталоге.

### 10.3 Факт — в каждом ответе

Каждый завершённый job несёт `cost.charged_credits` (и `quoted_credits` для сверки); каждый
LLM-ответ — `credits_charged` (§9.1). Это идёт в наши метаданные истории генераций: у ассета
в проекте видно, во что он обошёлся.

### 10.4 История трат

```json
GET /v1/billing/usage?from=2026-07-01&to=2026-08-01&cursor=…
→ 200
{ "items": [ { "at": "2026-07-31T18:02:11Z", "job_id": "job_01j9x7v3",
               "type": "image.generate", "credits": 8, "client_id": "pix3-editor" } ],
  "next_cursor": null }
```

С разбивкой по `client_id` — чтобы пользователь видел, сколько именно Pix3 потратил.

### 10.5 Ноль кредитов и лимиты

- Баланс исчерпан → **`402` с кодом `insufficient_credits`** и полем
  `details.required_credits`. Отдельный код обязателен: наш UI по нему показывает не «ошибка
  сети», а «пополните баланс Strophe» со ссылкой.
- Превышен лимит гранта (§3.2) → `403 spend_limit_exceeded` + `details.limit`,
  `details.resets_at`.
- Job, частично выполненный к моменту исчерпания, — договоримся: наша рекомендация — quote
  резервируется при создании job (`hold`), списывается по факту завершения; тогда «кончились
  кредиты посреди job» невозможно by design.

## 11. Таксономия ошибок

Единый конверт для всех эндпоинтов (и для поля `error` в failed job):

```json
{ "error": {
    "code": "moderation_blocked",
    "message": "Input image was rejected by the safety filter.",
    "retry_after": null,
    "details": { "stage": "input", "categories": ["violence"] },
    "request_id": "req_8ab12"
} }
```

Обязательный набор кодов и их маппинг на наши внутренние типы ошибок
(`kind` в `ImageGenError`/`LlmError`):

| HTTP | `code` | Наш `kind` | Комментарий |
|---|---|---|---|
| 401 | `invalid_token`, `token_expired` | `missing-key` | по `token_expired` — тихий refresh и ретрай |
| 402 | `insufficient_credits` | (новый kind) | отдельный UX «пополните баланс» |
| 403 | `insufficient_scope`, `spend_limit_exceeded` | `missing-key` / (новый) | |
| 404 | `not_found` | `http` | job/file/model не существует |
| 409 | `idempotency_conflict` | `http` | тот же ключ, другое тело |
| 422 | `invalid_input` | `http` | валидация; `details.field` укажет поле |
| 422 | `moderation_blocked` | `blocked` | отказ модерации, вход или выход; различайте `details.stage` |
| 429 | `rate_limited` | `http` + ретрай | **обязателен `Retry-After`** |
| 499/— | `cancelled` (статус job) | `aborted` | отмена клиентом |
| 5xx | `internal`, `upstream_error`, `overloaded` | `http`/`network` | `overloaded` + `Retry-After` |

Два принципиальных требования:

1. **`moderation_blocked` — всегда отдельный код**, никогда не generic 400 и не «success с
   пустым результатом». Наш UI объясняет пользователю отказ модерации иначе, чем баг.
2. **Job, завершившийся без артефактов, — это `failed` с ошибкой**, а не `succeeded` с пустым
   массивом. (В нашей таксономии «пришёл успех без картинки» — отдельный вид ошибки `empty`
   именно потому, что провайдеры этим грешат.)

## 12. Детерминизм и вариации

- **`seed`** принимается в input везде, где осмыслен (image, video, audio, pipeline), и
  **возвращается в каждом артефакте** — даже когда клиент его не задавал (сервер сгенерировал
  сам). Мы пишем seed в метаданные ассета: «перегенерируй такой же, но…» — базовый сценарий.
- Воспроизводимость — best effort, честно задокументированная: тот же `model` + `input` +
  `seed` + та же версия модели ⇒ тот же результат. Смена версии модели под тем же id ломает
  это — поэтому либо версия в id модели (`img/flux-pro-1.1`), либо поле `model_version` в
  артефакте.
- **Вариации**: `POST /v1/jobs` с `"variation_of": "job_01j9x7v3"` — сервер берёт рецепт
  исходного job (все input), применяет присланные оверрайды и новый seed. Избавляет клиента
  от необходимости хранить и пересобирать полный input.

## 13. Пайплайны как вызываемые эндпоинты — ваш главный дифференциатор

Сырые модели есть у всех. Нодовые воркфлоу, опубликованные как **типизированные endpoints**, —
то, чего нет у generic-провайдеров и что закрывает пол-конвейера редактора одним вызовом.

### 13.1 Почему это ценно именно нам

«Рецепт игрового ассета» — это никогда не один вызов модели. Типичный спрайт:
сгенерировать → убрать фон → апскейл → обрезать по контенту → PNG с альфой нужного размера.
Сегодня Pix3 делает это сам: генерация у провайдера, удаление фона — локально в Web Worker
(две нейронки в браузере!), обрезка/ресайз — канвас-код. Если тот же рецепт — одна нода-цепочка
у вас и один `pipeline.run` у нас, мы выкидываем клиентскую половину конвейера, а пользователь
получает предсказуемый результат за фиксированную цену в кредитах.

### 13.2 Контракт

- Сохранённый воркфлоу публикуется как пайплайн с `id`, целочисленной `version`,
  `input_schema` (JSON Schema), декларацией `output_artifacts` (роли/mime) и ценой — всё это
  уже показано в каталоге (§7).
- Вызов — та же job-модель:

```json
POST /v1/jobs
{ "type": "pipeline.run",
  "pipeline": "strph/sprite-with-alpha@3",
  "input": { "prompt": "red potion bottle, fantasy icon", "style_ref": "file_9f2c1", "target_size": 512 } }
```

- **Пиннинг версии обязателен** (`@3`). `@latest` допустим, но клиент, которому важна
  воспроизводимость, пиннится. Обновление пайплайна автором не должно молча менять поведение
  под закреплённой версией.
- Валидация input по schema — на вашей стороне, ошибки как `422 invalid_input` с `details.field`.
- Вопрос-развилка: чьи пайплайны видны через API — только официальные Strophe, или и
  пользовательские опубликованные? Наша рекомендация — оба, с неймспейсом в id
  (`strph/…` vs `user/…`) и одинаковым контрактом.

### 13.3 Как редактор покажет ваши пайплайны: «пресеты ассетов»

Pix3 может отрисовать каждый пайплайн из каталога как пресет в диалоге генерации: заголовок,
описание, форма из `input_schema` (мы уже генерируем UI из схем свойств — это наш родной
паттерн), цена в кредитах на кнопке. То есть автор воркфлоу в Strophe публикует «рецепт
ассета» — и он немедленно становится кнопкой в чужом редакторе, с оплатой вашими кредитами.
Это ваш маркетплейс-потенциал; от нас для этого нужен только каталог с честными схемами.

## 14. Геймдев-пресеты: что мы просим завести как пайплайны/ноды

Generic-платформы этого обычно не имеют, а для движка это хлеб. Каждый пункт — кандидат в
официальный пайплайн Strophe (см. §13); одной строкой — почему это важно движку:

1. **Спрайт с прозрачным фоном + обрезка по контенту** — базовая единица 2D-игры; альфа и
   плотный bounding box экономят филлрейт и упрощают коллизии.
2. **Бесшовные тайлящиеся текстуры** (`tileable: true`) — фоны и terrain тайлятся; шов виден
   мгновенно и правится только генерацией.
3. **PBR-наборы** (albedo/normal/roughness/AO как отдельные артефакты с ролями
   `texture.*`) — 3D-материал движку нужен комплектом, а не одной картинкой.
4. **Консистентность персонажа между кадрами + спрайт-листы** (`role: "spritesheet"` +
   `role: "atlas.json"` с раскладкой кадров) — анимация требует один и тот же персонаж в N
   позах; атлас — наш нативный формат.
5. **Наборы иконок в едином стиле** (style reference / переиспользуемый style id поверх
   `/v1/files`) — UI из 30 иконок обязан выглядеть одним сетом, иначе интерфейс рассыпается.
6. **UI-панели под 9-slice** (генерация с симметричными краями и равномерной центральной
   зоной; в meta — предлагаемые инсеты) — панели растягиваются без артефактов только при
   9-slice-совместимой геометрии.
7. **Пиксель-арт с точной сеткой и палитрой** (`grid: 32`, `palette: [...]` или пресет) —
   «пиксель-арт» от обычной модели плывёт по сетке; движку нужны честные пиксели без
   сглаживания.
8. **3D с бюджетом полигонов и PBR в GLB** — WebGL/мобильный бюджет; см. §8.2.
9. **One-shot SFX** с точной длительностью и без хвоста тишины — звук клика в 400 мс, не в
   3 секундах WAV.
10. **Бесшовно лупящаяся музыка** (`loop_start_ms/loop_end_ms`) — фоновая музыка в игре
    крутится часами, щелчок на стыке слышен каждые 30 секунд.
11. **TTS по локалям** — у нас система локализации; реплика × N языков одним батчем.

Не просим всё сразу — просим, чтобы **форма API** (роли артефактов, схемы пайплайнов,
style-референсы) позволяла добавлять такие пресеты без изменения контракта.

## 15. Права на результат, приватность и хранение

Для нас это не юридическая формальность, а поле в API. Pix3 — движок: сгенерированный ассет
уезжает в игру, которую пользователь публикует и продаёт. Ассет с неясными правами нельзя
шипнуть, и мы не можем позволить пользователю узнать об этом постфактум.

- **Коммерческие права — машиночитаемо, на элемент каталога.** В `models[]`/`pipelines[]`
  просим поле вида:

  ```json
  "usage_rights": {
    "commercial": true,
    "attribution_required": false,
    "notes_url": "https://strophe.app/legal/models/flux-pro"
  }
  ```

  Разные модели под капотом приходят с разными лицензиями — если это различие есть, оно должно
  быть видно в каталоге, а не спрятано в общем ToS. Мы покажем его в пикере моделей и, при
  `commercial: false`, предупредим прямо в диалоге генерации.
- **Кому принадлежит результат.** Зафиксируйте однозначно: права на выход у пользователя,
  сгенерировавшего его. Если есть исключения (например, обучение на пользовательских
  генерациях) — тоже в явном виде.
- **Приватность промптов и входов.** Игры в разработке конфиденциальны: промпты, скриншоты
  сцены и референсы — это незарелизенный контент. Нужен ответ на два вопроса: используете ли
  вы их для обучения (и есть ли opt-out на уровне аккаунта/гранта) и сколько храните.
- **Retention артефактов и файлов.** Мы просим ≥ 7 дней на артефакты (§5) и ≥ 30 дней на
  файлы (§6), а также возможность удалить: `DELETE /v1/files/{id}` и
  `DELETE /v1/jobs/{id}` (удаляет артефакты). Пользователь должен уметь стереть свой контент
  с вашей стороны, не заводя тикет.
- **Провенанс.** Если вы штампуете C2PA/метаданные в файлы — скажите об этом в каталоге
  (`provenance: "c2pa"`), потому что часть наших пользователей чистит метаданные при экспорте
  билда, а часть, наоборот, обязана их сохранять.

## 16. Приоритеты интеграции

### P0 — без этого интеграция невозможна

- CORS на всех эндпоинтах **и на CDN артефактов** (§2.2).
- Браузеро-безопасная аутентификация: минимум device-code flow + короткоживущие scoped-токены
  с лимитом трат и отзывом (§3).
- Job-модель: `POST /v1/jobs` + `GET /v1/jobs/{id}` (поллинг), отмена, `Idempotency-Key` (§4).
- `image.generate` с полями §8.1 (включая `background: "transparent"` хотя бы у одной модели
  или через пайплайн).
- Каталог с capabilities и ценами в кредитах (§7).
- Таксономия ошибок §11, включая `insufficient_credits` и `moderation_blocked`.
- `GET /v1/billing/balance` и `cost.charged_credits` в job.
- Ясность с коммерческими правами на результат (§15) — хотя бы одним общим утверждением
  «всё, что сгенерировано, можно использовать коммерчески»; иначе мы не можем предлагать
  генерацию для продакшен-ассетов.

### P1 — важно, ждём в первых версиях

- LLM-лана: OpenAI-совместимые `/v1/chat/completions` + `/v1/models` с tools, streaming,
  usage-кэшем, `reasoning_effort` (§9). (Технически для нас это почти P0 — интеграция
  нулевая, ценность немедленная; выделено в P1 только потому, что генерация без LLM имеет
  смысл, а наоборот — тоже.)
- SSE-прогресс (§4.4) и `progress` у 3D.
- `/v1/files` с дедупом (§6).
- `model3d.generate` (§8.2).
- `POST /v1/quote` (§10.2) и `GET /v1/billing/usage` (§10.4).
- `pipeline.run` + пайплайны в каталоге (§13) — как только у вас есть публикация воркфлоу.
- `seed` в артефактах и `variation_of` (§12).

### P2 — nice-to-have

- Аудио-модальности (§8.4) — у нас пока нет аудио-UI, но контракт готовы принять заранее.
- `video.generate`.
- Anthropic-совместимый `/v1/messages` (§9.2).
- Батч-TTS по локалям, style id как первоклассный объект, inline `response_format`.
- Геймдев-пресеты §14 — по мере появления, форма API уже всё позволяет.

### Что мы честно возьмём в первую же версию

При наличии P0: **картинки + баланс + ошибки** — Strophe появляется в пикере Image Generation
у всех пользователей Pix3. При наличии OpenAI-совместимой LLM-ланы — одновременно и в пикере
моделей агента. 3D, пайплайны-пресеты и аудио подключим следующими итерациями по мере
появления на вашей стороне; адаптер под job-модель у нас будет общий с первого дня.

## 17. Открытые вопросы к команде Strophe

1. OAuth (device/PKCE) в v1 — реалистично? Если нет — согласны на «browser key» с
   обязательными TTL/scopes/лимитом трат как временную меру (§3.3)?
2. Резервирование кредитов на job (`hold` по quote при создании, списание по факту) — ложится
   на ваш биллинг? Нам важно только «нет списаний за незавершённое сверх потреблённого».
3. Пайплайны в API: только официальные или и пользовательские опубликованные? Наша
   рекомендация — оба с неймспейсами (§13.2).
4. Гибрид `Prefer: wait=` (§4.2) — ок, или чистый async для всех job? Оба варианта нам
   подходят, чистый async требует SSE.
5. Какие модальности реально будут под капотом на старте (image / 3D / video / audio / LLM)?
   Мы расставили приоритеты в §16 — синхронизируем с вашим роадмапом.
6. Есть ли у вас нода удаления фона / апскейла / обрезки уже сейчас? Если да — пайплайн
   §13.1 («спрайт с альфой») мы просим первым официальным пресетом.
7. Коммерческие права на результат (§15): одинаковы для всех моделей или зависят от модели
   под капотом? Если зависят — сможете отдавать `usage_rights` в каталоге?
8. Есть ли ограничения на регион/резидентство данных и оплату для пользователей вне РФ?
   У Pix3 аудитория международная, и это влияет на то, как мы позиционируем Strophe в UI
   (единственный биллинг или один из вариантов).
