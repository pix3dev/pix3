# External agent authoring — свой агент пишет игру, редактор доводит её руками

Status: **план, не начат** · Date: 2026-09-25 · Ревизия 2 (после внешнего ревью и контрольного ревью: гонки записи, барьер
синхронизации, идентичность папки, доверие к локальным процессам, строгая валидация, доставка) ·
Заменяет удалённый `frozen/headless-agent-authoring-pipeline.md`

## 1. Цель

Пользователь, привыкший к своему агенту (Claude Code, Codex, Cursor, …), делает Pix3-игру **в своей
среде**: без API-ключей в редакторе, без чата внутри редактора, без ручной настройки мостов для
базового пути. Агент получает от нас набор инструментов и базу знаний, пишет настоящий Pix3-проект
(сцены, скрипты, ассеты), а человек в любой момент открывает этот же проект в редакторе и двигает
объекты мышкой — вместо бесконечного «сдвинь кнопку на 20px левее» промптами. Агент видит ручные
правки, человек видит правки агента.

Целевой сценарий, который план обязан сделать правдой:

```text
$ npx @pix3/cli new tapper my-game        # рецепт + agent kit, ~2 c, без сети к LLM — уже играбельно
$ cd my-game && claude                    # или codex
> игра: ловим падающие звёзды, неон, 60 секунд
  … ≤30 c …  рецепт переделан под запрос, `pix3 check` зелёный
[человек открывает папку в редакторе, двигает HUD, меняет цвет фона, Ctrl+S не нужен]
> звёзды слишком медленные, и добавь комбо
  … агент перечитывает сцену с правками человека, меняет скрипт, запускает игру в редакторе
    (ровно ту версию файлов, что на диске), получает ошибки/скриншот через MCP, чинит …
```

Метрика скорости — **время от просьбы пользователя до проверенного изменения** (§7), а не до
«первого играбельного»: рецепт играбелен ещё до первого промпта.

### 1.1 Путь пользователя, который пришёл на сайт (а не из исходников)

Пользователь не клонирует репозиторий: у него есть браузер, `editor.pix3.dev` и свой агент. Из
этого следуют ограничения: File System Access есть только в Chromium-браузерах на десктопе; сайт не
знает абсолютных путей и не может открыть папку без клика пользователя по системному пикеру; агент
не видит облачные проекты; Node у пользователя Claude Code / Codex уже есть (оба ставятся через npm).

Два входа, которые сходятся в одном состоянии: папка проекта на диске и та же папка открыта в редакторе.

**Вход с сайта (основной — пользователь сам ничего не ставит):**

1. `editor.pix3.dev` → «Новый проект» → рецепт → **«Работать со своим агентом»**.
2. Пикер «выберите, где создать папку» (один клик, неизбежен). Редактор пишет рецепт и agent kit;
   начиная с фазы 3 — ещё и MCP-конфигурацию (`.mcp.json` для Claude Code, аналог для Codex —
   проверить в фазе 0) с **закреплённой** версией CLI (§5 A).
3. Экран «Продолжите в своём агенте» с копируемыми командами: `cd <имя-папки> && claude` (или `codex`)
   и готовым первым промптом из выбранного рецепта. Редактор остаётся открытым и ждёт.
4. (Фаза 3+) Агент стартует и сам поднимает MCP из конфигурации (`npx -y @pix3/cli@<версия> mcp`);
   окно редактора находит его и подтверждает, что это та же папка (§1.2), и показывает «агент
   подключён». Bridge пользователь не ставит.
5. Дальше: двигает мышкой, пишет агенту. В следующий раз — проект из «Недавних» (один клик
   «разрешить доступ», браузер хранит handle).

**Вход из терминала (для тех, кто не хочет начинать с сайта):**

1. `npx @pix3/cli new tapper my-game && cd my-game && claude`.
2. Пользователь открывает Pix3 (PWA) → «Открыть папку» → `my-game` (один раз; дальше — «Недавние»).
3. Окно и агент находят друг друга сами (§1.2).

### 1.2 Как агент и редактор находят друг друга (без токенов и без bridge)

Редактор предполагается установленным PWA в отдельном окне (`display: 'standalone'`,
`vite.config.ts`). Любая схема «напечатать ссылку с токеном» здесь не работает: ссылка из
терминала открывается в обычной вкладке, а не в PWA-окне.

**Обнаружение.** `pix3 mcp` — stdio MCP-сервер, который агент сам запускает из конфигурации, и
одновременно крошечный HTTP-сервер на `127.0.0.1`, порт из фиксированного диапазона (например
`8490–8499`: первый свободный). При старте процесс генерирует случайный `sessionId`. PWA с открытым
проектом раз в пару секунд опрашивает диапазон `GET /hello` → `{ projectId, sessionId, protocol,
cliVersion, agent?, pid? }`. `projectId` из `pix3project.yaml` здесь — **только фильтр кандидатов**:
копия проекта, второй checkout или worktree несут тот же id.

**Подтверждение, что это та же физическая папка (challenge).** Для кандидата с совпавшим
`projectId` окно делает `POST /claim`; сервер пишет в **свой** каталог проекта файл
`.pix3/link/<случайное имя>` со случайным nonce и отвечает только именем файла. Окно читает этот
файл через свой FSA-handle и отвечает `POST /claim/confirm { nonce }`. Прочитать nonce может только
окно, чей handle указывает на тот же каталог (копия/worktree файла не увидят). Сервер удаляет
файл сразу после подтверждения или по таймауту 10 с.

**Одно обслуживающее окно.** Успешный claim даёт окну **аренду** (lease) на этот `sessionId`,
которая продлевается long-poll'ом `GET /calls`; без опроса ~10 с аренда истекает. Второе окно
того же проекта получает `busy` и показывает «агент обслуживается другим окном — [Перехватить]»
(перехват явный, старое окно получает отказ на следующем опросе). Между вкладками одного origin
владельца выбирает Web Lock (`navigator.locks`, имя по `projectId`); аренду канала может взять
только его держатель, и автосохраняет тоже он (§5 C4) — один владелец на оба дела, «Перехватить»
переносит их вместе (§4.3, «Несколько окон»).

**Граница доверия — честно.** Каналу не нужен токен, но не потому, что «угрозы закрыты»:

- **чужие сайты** не говорят с сервером: сервер отвечает только `Origin: https://editor.pix3.dev`
  (и dev-origin'ам), а сайт подделать `Origin` не может;
- **локальные процессы того же пользователя в модели угроз считаются доверенными** в той же
  мере, в какой они уже могут писать файлы проекта. Такой процесс может поднять свой сервер в той
  же папке и пройти challenge — защиты от этого у нас нет, и мы её не заявляем. `agent` и `pid` в
  `/hello` самозаявленные и в UI помечаются как неподтверждённые;
- единственный актив, который канал добавляет, — **ключи генерации в редакторе**. Поэтому
  `generate_*` требуют подтверждения в редакторе, **привязанного к конкретному подключению**
  (`sessionId` + аренда): «Процесс `npx @pix3/cli mcp` (называет себя: Claude Code, не
  проверено) в my-game хочет генерировать ассеты — разрешить на эту сессию». Переподключение,
  новый процесс или перехват аренды — разрешение сбрасывается. Плюс лимит на сессию (например 20
  генераций, дальше — повторный запрос) и кнопка отзыва. Это защита от **тихой** траты ключей, а
  не от процесса, который выдаёт себя за агента: такой процесс увидит человек в запросе.

**Системный запрос браузера.** Chrome спросит один раз разрешение **Local Network Access** при
первом обращении `https`-страницы к `127.0.0.1`. LNA — это новый механизм на основе разрешения,
он заменил прежний Private Network Access с его preflight-заголовками
(`Access-Control-Request-Private-Network`, которые сейчас обрабатывает bridge,
`tools/pix3-agent-bridge/src/index.ts:274`). Опираться на PNA-preflight нельзя; что именно нужно
от сервера и от `fetch` в установленном PWA (в том числе для long-poll), проверяет фаза 0
(https://developer.chrome.com/blog/local-network-access).

**Совместимость версий.** `protocol` — отдельное целое число протокола канала, не lockstep-версия
продукта (она ничего не обещает про API). Редактор объявляет поддерживаемый диапазон; при
несовпадении окно и инструмент отвечают конкретно: «кэшированный редактор старее проекта —
перезагрузите PWA» или «CLI в проекте старее редактора — `pix3 kit --update`».

**Bridge на этом пути не участвует вообще.** Он остаётся тем, чем был: провайдерные лейны и
подписки для встроенного агента. Его проблема с доставкой `#bridge-token` в PWA-окно — отдельный
баг существующего спаривания, не этого плана (вероятное решение — страница `/pair`, которая
кладёт токен в общее хранилище origin и шлёт его PWA-окну через `BroadcastChannel`).

**Что не поддерживаем в v1 и честно говорим на сайте:** Safari/Firefox (нет File System Access →
кнопка «Работать со своим агентом» скрыта с объяснением), мобильные, облачные/collab-проекты.
Если трение пикера и Chromium-only окажется главным — локальный сервер `pix3 mcp` как workspace-адаптер (редактор
читает папку через loopback, без пикера и в любом браузере) — отдельное решение после фазы 3,
это новый backend `ProjectStorageService`, M/L.

**Главный сдвиг позиционирования:** основной автор — внешний агент; наша ценность — формат,
движок, редактор и проверка, а не собственный LLM-цикл. Встроенный агент остаётся, но перестаёт быть
единственной дверью (его скорость — отдельный трек §8).

## 2. Почему не headless-хост (решение по старому плану)

Замороженный план строил второй браузерный хост без PWA, управляемый bridge (session broker,
browser manager, транзакции, ревизии, параллельные Chromium). Он решал задачу **автономных
прогонов без человека**, а наша задача обратная — агент и человек над одним проектом при открытом
редакторе. Headless-хост не убирал установку bridge, не давал человеку видеть правки агента и
никак не ускорял агента (тот же цикл хопов плюс WebSocket). Оценка — L+ (одна фаза мутаций была L).
Проверка без редактора остаётся как узкая условная фаза 4 (§6).

## 3. Что уже есть (проверено по исходникам 2026-09-25)

- **Редактор уже подхватывает внешние правки открытой сцены и скриптов.** `FileWatchService`
  (`src/services/project/FileWatchService.ts`) опрашивает раз в 2,5 с; внешняя запись сцены →
  `ReloadSceneCommand` (`src/ui/pix3-editor-shell.ts`, `handleFileChanged`); скрипты
  перекомпилируются (`ProjectScriptLoaderService`). Дыры:
  1. опрос стоит на паузе, пока окно **не в фокусе** (`isDocumentActive` требует `hasFocus()`,
     `src/services/core/page-activity.ts`) — то есть ровно тогда, когда человек пишет в терминал;
  2. опрос стоит на паузе **во время play** (`FileWatchService.ts:46–60`, `shouldPoll`) — агент,
     записавший файлы и сразу запустивший игру, проверит старую версию;
  3. новые/удалённые файлы не видны — `fileRefreshSignal` бампают только внутренние записи
     (`ProjectService.ts`, `ProjectStorageService.ts`);
  4. reload молча заменяет граф и **чистит историю** (`ReloadSceneOperation.ts`; `handleFileChanged`
     не смотрит на dirty-флаг), даже если в сцене есть несохранённые правки человека; префаб-инстансы
     обновляются (`RefreshPrefabInstancesCommand`) только если сам префаб открыт во вкладке —
     следят лишь за открытыми сценами;
  5. автосохранения в Studio нет — ручная правка попадает на диск только по Ctrl+S, и агент читает
     устаревший файл;
  6. сравнение только по `lastModified`, без содержимого: нельзя ни отличить «агент записал то же
     самое», ни сказать, какую версию файла редактор сейчас держит.
- **Все инструменты редактора уже исполнимы извне** — `window.__PIX3_DEBUG__.agentTools.execute()`
  (`src/core/debug-bridge.ts`), но только в dev-сборке и через chrome-devtools. Это доказывает, что
  живой канал — тонкий адаптер к `AgentToolRegistry`, а не новый хост.
- **Bridge умеет парковать MCP-вызовы и отдавать их вкладке** (`tools/pix3-agent-bridge/src/tool-relay.ts`,
  stdio-shim `mcp-shim.ts` для `agy`), но только для сессий, которые bridge запустил сам. Маршрута,
  через который внешний Claude Code/Codex зовёт инструменты открытого редактора, нет.
- **Рецепты — это просто папки файлов** (`src/templates/projects/recipe-*/files/` + `template.yaml`):
  сцены, скрипты, `design/recipe.md`, routines в `design/tests/`. Копируются без редактора.
- **Знания для агента уже написаны**, но не упакованы для внешнего агента: `docs/pix3-specification.md`
  («Scene File Format»), `docs/node-types-reference.md`, `src/services/agent/agent-skills/*.md`
  (`engine-api-map.md`, `game-prototype.md`, `verify-and-fix.md`, `asset-generation.md`).
- **Guard'ы живут только в тулах**: `emoji-as-art.ts` и проверки `set_property`/`create_node`
  отрабатывают при вызове тула; YAML, записанный руками, их обходит.
- **Загрузчик намеренно прощающий.** `SceneLoader` бросает `SceneValidationError` на структурных
  ошибках, но неизвестный `type:` по спецификации становится инертным `NodeBase` («Forgiving
  Vocabulary», `docs/pix3-specification.md` → «Scene File Format»; предикат `isInertNode` в
  `packages/pix3-runtime/src/core/renderability-lint.ts`). Успешная загрузка ≠ валидная сцена —
  строгий профиль нужно строить поверх (§5 A). Сотни persistence-спеков грузят сцены под
  happy-dom, то есть в Node загрузка в принципе работает.

## 4. Архитектура

Три слоя, каждый полезен без следующего:

```text
 ┌──────────── агент пользователя (Claude Code / Codex / …) ────────────┐
 │ читает agent kit в проекте · пишет файлы · зовёт CLI · MCP           │
 └───────┬───────────────────────┬──────────────────────────┬───────────┘
         │ файлы                  │ shell                    │ MCP stdio
         ▼                        ▼                          ▼
 ┌── папка проекта ──┐   ┌── pix3 new / validate / check ── pix3 mcp ──┐
 │ pix3project.yaml  │◄──│ @pix3/cli (Node, без браузера)   127.0.0.1: │
 │ scenes/ scripts/  │   │                                  парковка,  │
 │ sprites/ design/  │   │                                  хеши диска │
 │ AGENTS.md, skills │   └──────────────────────────────────┬──────────┘
 │ .pix3/ (recovery, │    /hello → claim (challenge-файл) → │ long-poll
 │  link, tsconfig)  │    аренда, вызовы с хешами файлов    ▼
 └────────▲──────────┘                                ┌── редактор (PWA) ─────┐
          │ File System Access (чтение/запись, опрос) │ play, routines, ошибки│
          └───────────────────────────────────────────│ скриншоты, generate_* │
                                                      └───────────────────────┘
```

### 4.1 Контракт — файлы проекта на диске

Истина — папка проекта. Агент пишет `.pix3scene`, `scripts/*.ts`, ассеты обычными средствами своей
среды. Второго формата, authoring-RPC для мутаций, транзакций и ревизий **нет**: откат — git,
проверка — `pix3 check`. MCP-канал в v1 **не мутирует сцены** (единственный путь записи — файлы;
исключение — `generate_*`, который кладёт ассет файлом).

**Атомарность не обещаем — обещаем поведение на промежуточном состоянии.** Инструменты агента
могут писать через truncate+write или несколькими правками подряд, а пачка «скрипт + префаб +
сцена» не согласована даже при атомарной замене каждого файла. Поэтому редактор:

1. **ждёт стабилизации**: изменение принимается, когда два последовательных снимка набора
   изменённых файлов (размер + хеш содержимого) совпали с интервалом ≥ 300 мс — вся «пачка»,
   попавшая в одно окно тишины, загружается вместе;
2. **держит последний успешно загруженный граф**: если сцена/префаб не парсится или зависимость
   ещё не готова (скрипт не скомпилирован, префаб отсутствует), граф не заменяется; окно
   повторяет попытку с backoff, а через ~5 с неуспеха показывает ошибку загрузчика на сцене
   («файл не читается: …») — без потери состояния;
3. **не запускает проверку до завершения синхронизации** — это барьер из §5 D.

Kit советует агенту писать через временный файл + rename, где его инструменты это умеют, но
корректность от этого не зависит.

### 4.2 Базовый путь не требует ключей и bridge

`new` + agent kit + `validate`/`check` работают офлайн и без редактора. Живой канал
(play/скриншот/ошибки/генерация в открытом редакторе) тоже не требует bridge: его поднимает сам
агент из MCP-конфигурации (§1.2).
Арт на базовом пути — плейсхолдеры (`ColorRect2D`, плейсхолдеры рецепта) и SVG-спрайты, которые
агент пишет сам; растровая генерация — через MCP → `generate_asset` редактора (его провайдеры,
если у пользователя они настроены), либо собственные инструменты агента (у Codex есть генерация картинок).

### 4.3 Редактор — полноправный соавтор; обещание про ручные правки

Автосохранение + плашка **не закрывают** гонку записи: агент может прочитать сцену, человек —
изменить её и дождаться автосохранения, затем агент — записать свою устаревшую версию поверх;
редактор к тому моменту считает сцену чистой. Обратная гонка: автосохранение затирает файл агента
до следующего опроса. Проверка хеша перед записью между двумя независимыми писателями тоже не
атомарна. Строгую гарантию дал бы только согласованный протокол писателей (агент пишет через нас
или честно соблюдает блокировку) — это анти-скоуп v1, а просьба в kit «уважай lock-файл»
гарантией не является.

Поэтому обещание v1 сужено и зато выполняется архитектурой, без кооперации агента:

> **Ручная правка никогда не теряется безвозвратно и никогда не перезаписывается молча.**
> Любую версию, которую редактор записал на диск, можно восстановить; любой случай, когда файл
> агента не содержит ручных правок, редактор замечает и показывает, а не принимает тихо.

Механизм (§5 C3–C4):

- **Журнал восстановления** `.pix3/recovery/` (kit добавляет `.pix3/` в `.gitignore`): каждая
  версия, записанная автосохранением, и каждая ручная версия, которую редактор собирается
  заменить внешней, кладётся туда до замены. Кольцо по размеру/возрасту (например 200 версий или
  7 дней). Если запись в папку невозможна — копия в IndexedDB.
- **База для сравнения.** Для каждой сцены редактор помнит `B` — последнюю версию, пришедшую
  **извне** (загрузка/внешний reload), и `E` — последнюю, записанную им самим (между двумя
  внешними версиями автосохранений может быть много — `E` всегда последнее, `B` не двигается).
  Ручные правки с момента `B` — это `diff(B → E)` по id нод и свойствам. Все хеши — от **байтов
  прочитанного/записанного файла**, никогда от повторной сериализации `SceneSaver`.
- **Трёхсторонний разбор внешней версии `A` по каждому свойству, которое человек менял**
  (`B.p ≠ E.p`), — решение на уровне свойства/ноды, а не сцены:
  - `A.p == E.p` — агент перечитал и сохранил правку: ничего не делать;
  - `A.p == B.p` — **сигнал устаревшей записи**: агент писал поверх старого чтения. Правило
    «сначала человек»: значение `E.p` возвращается в граф;
  - `A.p` — новое значение (≠ `B.p`, ≠ `E.p`) — агент сознательно поставил своё поверх свежего
    чтения: принимается версия агента, запись в merge-log, мягкая подсветка ноды, без плашки.
  Свойства, которые человек не менял, всегда берутся из `A`. Структура: нода есть в `E`, нет в
  `B` и нет в `A` — агент её не видел → сигнал устаревшей записи, нода возвращается; нода есть в
  `B` и нет в `A` — агент её удалил намеренно (он её видел в любом чтении) → удаление
  принимается, ручная версия в журнале, запись в merge-log.
- **Итог разбора записывается и не блокирует работу.** Если были сигналы устаревшей записи,
  редактор строит `M` = `A` + возвращённые ручные значения, применяет его к графу и сохраняет
  (с проверкой перед записью). Неблокирующая плашка: «Агент записал устаревшую версию — N ваших
  правок сохранено. [Принять версию агента для них]». Кнопка — обычная операция поверх текущего
  графа (с undo), поэтому правки, сделанные человеком после разбора, не теряются и отдельный
  «режим конфликта» с остановкой автосохранения не нужен. Переходы: тихий reload — `B := A`,
  `E := A`; разбор с возвратом — `B := A`, `E := M`.
- **Автосохранение сцены удерживается** только пока есть **неразобранная** внешняя версия: файл
  не стабилизировался, не парсится или зависимости не готовы (§4.1). Иначе проверка перед
  записью увидела бы чужой хеш, а автосохранение затёрло бы незаконченную запись агента. Ручные
  правки в это время копятся в графе и в журнале и проходят разбор, как только `A` загрузится.
- **Проверка перед записью.** Автосохранение перечитывает файл и сравнивает хеш с последним
  известным содержимым диска; не совпал — не пишет, а идёт в путь разбора. Остаточное окно
  (миллисекунды между проверкой и записью) может стоить **агенту** его записи, но не человеку:
  ручная версия в журнале. Агент узнаёт об этом по барьеру/`project_status` (они перечисляют
  файлы, изменённые редактором после последней записи агента) — kit велит перечитывать их.
- **Видимость для агента.** Каждое решение детектора пишется в `.pix3/merge-log.jsonl`
  (файл, свойства, чья версия победила); `pix3 check` и `project_status` показывают свежие записи.
  Так агент, намеренно вернувший старое значение, увидит, что редактор его «восстановил», и не
  будет гадать.

Неоднозначность честно остаётся в одном узком случае: агент мог прочитать свежую `E` и
сознательно вернуть свойство ровно к значению из `B` (или удалить ноду, которую человек только
что создал) — для редактора это неотличимо от устаревшей записи. Правило «сначала человек»
решает его в пользу ручной правки, видимо для обоих через merge-log; сознательно новое значение
агента (третий исход) ложного конфликта не даёт.

**Несколько окон.** Автосохраняет и обслуживает MCP одно и то же окно: Web Lock проекта и аренда
канала (§1.2) — один владелец и переходят вместе («Перехватить» = `steal: true` на Web Lock +
новая аренда). Окно в другом профиле браузера Web Lock не видит; его записи для владельца —
просто ещё один внешний писатель, и они проходят тот же разбор.

### 4.4 Скорость — забота agent kit, а не архитектуры

Быстрое проверенное изменение достигается тем, что агент **не проектирует с нуля**: `new <recipe>` даёт
работающую игру, kit говорит «сначала играбельное изменение, вопросы — после», а рецепт
описывает ручки (`design/recipe.md`). Замер Flow уже показал 12 с от рецепта до играбельного
скелета (`prompt-to-playable-flow.md` §11.8); внешний агент без наших хопов через bridge должен
быть не медленнее.

## 5. Компоненты

### A. `@pix3/cli` — новый пакет `packages/pix3-cli` (lockstep-версия, как остальные workspaces)

- `pix3 new [recipe] [dir]` — копирует рецепт/шаблон (шаблоны пакуются из `src/templates/projects/`
  при сборке пакета — один источник), пишет `pix3project.yaml` со стабильным `id`, ставит agent
  kit. Без аргумента — список рецептов с одной строкой описания из `template.yaml`.
- `pix3 validate [paths…] [--json]` — **строгий профиль** поверх настоящего `SceneLoader` (Node +
  happy-dom или минимальный DOM-shim — решает спайк фазы 0). Прощающая загрузка редактора не
  меняется; строгость живёт только здесь. Выход — список
  `{severity, code, file, nodeId?, path, message, fix?}`; `--json` для агента; код выхода 1, если
  есть хотя бы одна **ошибка**.
  - **Ошибки:** YAML не парсится / `SceneValidationError`; неизвестный `type:` (инертная нода по
    `isInertNode`, с подсказкой ближайшего имени из `describeUnknownNodeType`); неизвестный
    компонент (`core:` не в реестре, `user:` не найден в `scripts/`); неизвестное свойство ноды или
    компонента (нет в `getPropertySchema()`); значение не того типа / вне допустимого диапазона
    или enum по `PropertyDefinition`; отсутствующий `res://`-файл; отсутствующий или циклический
    префаб-инстанс; дубликат id ноды; guard'ы, вынесенные из тулов в общий модуль
    (`emoji-as-art`, прочие проверки `create_node`/`set_property`).
  - **Предупреждения:** renderability-lint (ноды вне экрана, нулевой размер, невидимые), неиспользуемые
    ассеты, устаревшая версия схемы файла (мигрируется при загрузке).
  - Что загрузчик делает сам (проверено по `packages/pix3-runtime/src/core/SceneLoader.ts`):
    дубликат id, отсутствующий/циклический префаб — бросает `SceneValidationError`; неизвестный
    `type:` — инертный `NodeBase` (стр. ~2109); неизвестные ключи `properties` — молча сохраняются
    (стр. ~929); значение не того типа — молча заменяется дефолтом (`typeof … ? … : undefined`);
    незарегистрированный компонент — `console.warn` и `pendingComponents`
    (`component-hydration.ts:113–133`); отсутствующий `res://`-ассет — `console.warn`, нода
    остаётся. Значит, строгий профиль — отдельный проход по `getPropertySchema()` и ссылкам поверх
    загрузки плюс перехват предупреждений загрузчика в ошибки. Каждый код ошибки покрыт фикстурой
    в спеке CLI. **Golden-тест против ложных ошибок:** все сцены и префабы рецептов/шаблонов
    (`src/templates/projects/`) и сохранённые редактором фикстуры проходят `validate` без единой
    ошибки — это ловит read-compat-алиасы и ключи, которые `SceneSaver` пишет вне
    `getPropertySchema()` (их список — белый список профиля, а не «неизвестное свойство»).
- `pix3 check` — `tsc --noEmit` по `scripts/` плюс то же, что `validate`, плюс свежие записи
  `.pix3/merge-log.jsonl`. **Откуда TypeScript и типы:** проект, созданный браузером, не имеет
  `node_modules` и не должен их требовать. `typescript` — зависимость самого CLI, а `.d.ts`
  `@pix3/runtime` той же lockstep-версии вшиты в пакет CLI при сборке. `check` генерирует
  `.pix3/tsconfig.check.json` с `paths` на типы внутри установленного CLI — без `npm install` в
  проекте. (`pix3 kit` дополнительно может положить `.pix3/types/` для подсветки в IDE.)
- `pix3 kit [--update]` — (пере)ставить agent kit в существующий проект (для проектов, созданных в
  редакторе, и после обновления CLI); обновляет версию kit в `pix3project.yaml` и, начиная с
  фазы 3, MCP-конфигурацию с закреплённой версией.
- `pix3 mcp` — **сам MCP-сервер** живого канала (§5 D).
- `pix3 setup [claude|codex]` — регистрация сервера в агенте для проектов без конфигурации:
  печатает/выполняет `claude mcp add pix3 -- npx -y @pix3/cli@<версия> mcp` и аналог для Codex.
  Для новых проектов не нужен.
- **Закрепление версий.** Любая записанная нами MCP-конфигурация вызывает
  `npx -y @pix3/cli@<X.Y.Z>` — той версии, что поставила kit, никогда не незакреплённый `@pix3/cli`
  (иначе `npx` возьмёт что угодно из кеша или реестра, и сервер разойдётся с kit и с кешированным
  PWA). Обновление — только явное, через `pix3 kit --update`. Совместимость с редактором
  определяет номер протокола (§1.2), а не версия пакета.
- **Гейт публикации для входа с сайта.** Деплой PWA и публикация `@pix3/cli` на npm — разные
  процессы, и lockstep-версия редактора может ещё не существовать в реестре — тогда `npx` в
  конфигурации падает. Редактор пишет в конфигурацию версию CLI, **подтверждённую в реестре**:
  номер кладётся в сборку PWA только после успешного `publish-packages.yml` (или деплой ждёт
  публикации), а редактор при записи дополнительно сверяет её с `registry.npmjs.org` и при
  недоступности берёт последнюю подтверждённую из манифеста сборки.

### B. Agent kit — то, что лежит в проекте

- `AGENTS.md` (читают Codex, Cursor и др.) + `CLAUDE.md` с `@AGENTS.md` + `.claude/skills/pix3-*/`
  (формат сцен, справочник нод, API скриптов, верификация, ассеты). Короткий корневой файл,
  детали — в skills, которые агент подгружает по необходимости.
- **Генерируется из существующих источников**, а не копируется руками: скрипт сборки CLI собирает
  kit из `docs/` и `agent-skills/`, spec-тест ловит дрейф. Иначе через месяц kit врёт. Kit
  собирается **под фазу**: раздел про MCP и `game_run` появляется только в сборке, где есть
  сервер, — промежуточный релиз не ссылается на отсутствующее.
- Ключевые правила kit (то, чего нет в текущих skills, ориентированных на встроенный цикл):
  1. сначала играбельное изменение рецепта, **вопросы — только после** того, как человек
     его увидел; не больше одного вопроса за ход;
  2. перед правкой сцены **перечитай файл** — человек мог её поменять в редакторе; после записи
     смотри вывод `check` на записи merge-log;
  3. раскладку, цвета и тонкую настройку оставь человеку: если просят «чуть левее» — поменяй, но
     предложи двигать в редакторе;
  4. после каждой пачки правок — `pix3 check`; при подключённом MCP — `game_run` с routine рецепта,
     и сверь, что в ответе проверена версия с твоими хешами (§5 D);
  5. арт: плейсхолдеры → SVG → `generate_asset` (если есть MCP), никогда эмодзи.

### C. Редактор: режим соавторства

1. **Опрос не зависит от фокуса окна**: `shouldPoll` = документ видим (не `hasFocus`); скрытая
   вкладка — редкий опрос + немедленная проверка на `visibilitychange`. Во время play опрос
   **обнаруживает** изменения (дёшево), но не перезагружает сцену; состояние помечается
   `stale`, и это видно в индикаторе и в ответах `play_status` / `game_observe`.
2. **Опрос дерева проекта**: новые/удалённые/изменённые файлы вне открытой сцены (префабы, ассеты,
   скрипты, `ui/`-сцены) → `fileRefreshSignal`, обновление браузера ассетов, перезагрузка
   затронутых префаб-инстансов. Дешёвый слой — `lastModified` + размер с бюджетом на число файлов;
   для изменившихся — хеш содержимого (`crypto.subtle.digest`), он же нужен детектору и барьеру.
   Стабилизация и «последний хороший граф» — §4.1. **`.pix3/` исключён** из опроса дерева,
   стабилизации, `expected` барьера и `fs.watch` сервера (там журнал, challenge-файлы,
   `tsconfig.check.json`); **собственные записи редактора** (автосохранение, журнал) узнаются по
   хешу и не входят в окно стабилизации — иначе активное перетаскивание мышкой не даёт набору
   «успокоиться».
3. **Неразрушающий reload и разбор внешних версий**: reload с сохранением камеры, выделения и
   раскрытых веток по id нод; база `B`/`E`, трёхсторонний разбор по свойствам, возврат ручных
   значений и неблокирующая плашка — §4.3. История после reload по-прежнему чистится (корректного undo через
   внешнюю правку нет — это осознанно), но про это говорит тост.
4. **Автосохранение привязанного проекта**: если проект содержит agent kit (или включено в
   настройках) — debounced-сохранение сцены после коммита операции (~1 с), с проверкой перед
   записью и журналом (§4.3), индикатор «на диске». Автосохраняет **только вкладка-владелец**
   Web Lock проекта (он же держит аренду канала, §4.3); автосохранение сцены удерживается, пока есть
   неразобранная внешняя версия, и на время барьера §5 D. Без
   автосохранения агент не видит ручных правок.
5. **Индикатор внешних правок**: короткая подсветка изменённых нод в дереве после reload — человеку
   видно, что сделал агент.
6. **`syncNow()`** — явная синхронизация по требованию (для барьера §5 D): немедленный скан дерева,
   ожидание стабилизации, загрузка изменённых сцен и зависимостей, ожидание окончания компиляции
   скриптов (`ProjectScriptLoaderService.ensureReady()` — уже есть: ждёт `scriptsStatus`
   `ready|error`, форсирует сборку в скрытой вкладке, таймаут 15 с). Возвращает хеши загруженных
   версий.

Точка проверки перед записью для C4 — перед `storage.writeTextFile` в
`src/features/scene/SaveSceneOperation.ts` (там же сейчас `setLastKnownModifiedTime`). Web Locks и
`BroadcastChannel` в `src/` пока не используются — это новая зависимость редактора.

### D. Живой канал: MCP в открытый редактор

- **Транспорт.** `pix3 mcp` — stdio MCP-сервер для агента и одновременно loopback HTTP-сервер для
  окна редактора; обнаружение, challenge, аренда и совместимость — §1.2. Вызов инструмента
  паркуется (по образцу `ToolRelay`, `tools/pix3-agent-bridge/src/tool-relay.ts`, — код можно
  вынести в общий модуль), окно-арендатор забирает его long-poll'ом `GET /calls` и отвечает
  `POST /calls/:id`. Браузер никогда не слушает порт. Нет окна с арендой — инструмент сразу
  отвечает «редактор не открыт / открыта другая папка — открой `<папка>` в Pix3», а не висит.
- **Барьер синхронизации — полный для `play_start`, `play_restart`, `game_run`.** Сервер стоит на
  стороне диска и знает, что там сейчас (хеши сцен, префабов, скриптов и `pix3project.yaml`,
  кеш по mtime + `fs.watch`). Окно перед запуском: **приостанавливает автосохранение** (правки
  человека копятся и сбрасываются после завершения запуска/`game_run`, так что барьер не гоняется
  с собственной записью редактора); останавливает play, если он идёт; вызывает `syncNow()`
  (§5 C6); передаёт серверу хеши загруженного. **`matchesDisk` считает сервер** — сравнением
  этих хешей с диском в момент ответа, а не со снимком до вызова; при расхождении окно повторяет
  синхронизацию до таймаута (~5 с), только потом запускает. Ответ содержит `revision` — хеши
  реально проверенных файлов, `matchesDisk` и список файлов, изменённых редактором после
  последней записи агента («изменён редактором — перечитай»), чтобы ручная правка не выглядела
  для агента провалом. Ошибки барьера отдельные и понятные: `sync_timeout` (со списком
  расходящихся файлов — например, агент ещё пишет), `load_failed` (ошибка загрузчика/компилятора с
  файлом и строкой), `pending_external` («`scenes/main.pix3scene` не читается уже N с —
  допиши/исправь файл»). Зелёный результат по старой версии файлов по построению невозможен.
- **Наблюдающие инструменты** (`play_status`, `game_input`, `game_observe`, `viewport_screenshot`,
  `read_errors`, `read_logs`) play **не останавливают** и не синхронизируют: они возвращают
  `revision`, с которой идёт текущая игра, и флаг `stale`, если диск изменился после её старта
  (§5 C1). Цепочка `play_start → game_input → game_observe` работает как ожидается; чтобы
  проверить новые файлы — `play_restart`.
- **Узкий набор инструментов (v1)**, поверх существующих хендлеров `AgentToolRegistry`:
  `project_status` (подключение, `revision`, неразобранные внешние версии, свежий merge-log),
  `play_start`/`play_stop`/`play_restart`/`play_status`, `game_run` (routines из
  `design/tests/`), `game_input`, `game_observe`, `read_errors`, `read_logs`,
  `viewport_screenshot` (картинкой в MCP-ответе), `generate_asset`, `generate_sfx`,
  `get_selection` (что человек сейчас выделил — «вот эту кнопку»). Мутаций сцены нет (§4.1).
- **Журнал на стороне диска.** Раз сервер всё равно следит за папкой, он кладёт в
  `.pix3/recovery/` и версии, которые видит от агента, — второй слой восстановления для
  остаточного окна гонки (§4.3), пока канал подключён.
- **Прозрачность**: в редакторе — компактный индикатор «агент подключён / синхронизация /
  выполняет `game_run`»; человек может отключить канал и отозвать разрешение генерации одной
  кнопкой.

## 6. Фазы

### Фаза 0 — спайк и замер (S+, ~4–5 дней). Решает, стоит ли дальше

Сначала рискованные механизмы, потом полировка kit:

- **Гонки записи.** Скрипт-«агент» пишет сцену по таймеру (truncate+write, rename, пачками), пока
  прототип автосохранения + детектора на `B`/`E` работает в редакторе; прогнать обе гонки из §4.3.
  Выход: детектор ловит все устаревшие записи, журнал содержит каждую ручную версию.
- **Барьер перед запуском.** Прототип `syncNow()` + сравнение хешей: запись файлов и сразу запуск
  проверяет новую версию, в том числе когда запись пришлась на play и на компиляцию скриптов.
- **Одна папка.** Challenge-файл против копии, второго checkout и git worktree с тем же
  `projectId`; две вкладки одного проекта (аренда + Web Locks). Проверить, передаётся ли
  `FileSystemHandle` через `BroadcastChannel` для `isSameEntry` между вкладками (запасной путь).
- **Транспорт LNA.** В установленном PWA на текущем стабильном Chrome: запрос Local Network
  Access появляется один раз и помнится, long-poll не режется, что нужно в ответах сервера и в
  `fetch`. Не опираться на PNA-preflight.
- **Холодный старт `npx`.** Время `npx -y @pix3/cli@<версия> mcp` с пустым кешем (со вшитым
  TypeScript) против таймаута запуска MCP-сервера в Claude Code и Codex; если не укладывается —
  разнести `mcp` и `check` по разным пакетам или лениво подтягивать TypeScript.
- **Строгий профиль.** `SceneLoader` в Node на всех сценах рецептов: какие DOM/canvas-зависимости
  вылезают; что загрузчик уже отвергает, а что молча принимает (неизвестные свойства, типы).
- **Агенты.** Руками скопировать рецепт, положить черновой `AGENTS.md` (склейка существующих skills),
  дать Claude Code и Codex по три задачи на трёх рецептах (tapper, arena, bouncer). Замерить:
  время от просьбы до изменения, которое проходит `validate`; число ошибок формата при открытии в
  редакторе; число ходов; вопросы без нужды.
- **Выход:** механизмы первых четырёх пунктов работают в прототипе; агент пишет валидные сцены в
  ≥ 2/3 прогонов, медиана «просьба → проверенное изменение» ≤ 60 с. Если YAML ломается
  системно — сначала чиним kit/формат-доки, CLI пока не строим; если не работает challenge или
  LNA — пересматриваем §1.2 до фазы 3.

### Фаза 1 — CLI + agent kit (M, ~1 неделя)

`new`, `validate` (строгий профиль), `check` (со вшитыми типами и TypeScript), `kit`; вынос
guard'ов в общий модуль; сборка kit из источников + spec на дрейф; публикация пакета тем же
`publish-packages.yml`. **MCP-конфигурацию фаза 1 не пишет**, kit без раздела про MCP — релиз
самодостаточен.
В редакторе — вход «Работать со своим агентом» при создании проекта (§1.1): пишет kit,
показывает экран с командами и первым промптом.
**Готово, когда:** на чистой машине (без глобального TypeScript, в папке без `node_modules`)
`npx @pix3/cli new <recipe>` + Claude Code / Codex по промпту из §1 дают проверенное изменение
(`pix3 check` зелёный) за медиану ≤ 30 с по 3 рецептам (≤ 60 с — допустимо), и проект открывается
и играет в редакторе без правок. Холодная установка (`npx` скачивание, пикер) меряется отдельно.

### Фаза 2 — соавторство в редакторе (M/L, ~1,5 недели)

Пункты §5 C 1–6, журнал восстановления, детектор и трёхсторонний merge (§4.3).
**Готово, когда:** правка агента видна в редакторе ≤ 3 с при окне без фокуса; ручное
перемещение ноды попадает на диск ≤ 2 с без Ctrl+S; в 20 прогонах каждой из двух гонок §4.3 и при
записи пачками/truncate+write **каждая ручная правка либо осталась в итоговом файле, либо
восстановима из журнала, и ни одна не заменена без плашки**, а сознательно новое значение агента
не даёт ложного возврата (spec на трёхсторонний разбор + живой
прогон скриптом-«агентом»); битый промежуточный файл не сбрасывает граф.

### Фаза 3 — живой канал MCP (M/L, ~1,5 недели)

§5 D целиком: `pix3 mcp` (stdio + loopback-сервер, хеши диска, журнал), `pix3 setup`, обнаружение +
challenge + аренда + проверка протокола в редакторе (§1.2), барьер синхронизации, подтверждение
`generate_*` на сессию, индикатор. `new`/`kit --update`/вход с сайта начинают писать
MCP-конфигурацию с закреплённой версией; kit получает раздел про MCP.
**Готово, когда:** установленное PWA-окно находит запущенного агента ≤ 3 с без единого клика
(кроме однократного запроса Local Network Access), в том числе когда окно не в фокусе;
копия/worktree с тем же `projectId` **не** подключается; вторая вкладка получает `busy`;
конфигурация подключает Claude Code, аналог — Codex; bridge не установлен; «записал → сразу
`game_run`» в 20 прогонах из 20 проверяет версию с хешами диска (`matchesDisk: true`) или
возвращает `sync_timeout`/`load_failed`/`pending_external`, никогда — зелёный результат по старой
версии; разрешение генерации сбрасывается при переподключении; расхождение протокола даёт
конкретную инструкцию.

### Фаза 4 — проверка без редактора (условная, M)

Только если фазы 1–3 покажут спрос на прогоны без открытого редактора (CI, фоновые агенты):
`pix3 play-check` — Playwright/CDP над player-сборкой (`player-main.ts`) с routines из
`design/tests/`, выдача ошибок и скриншота. Это то зерно старого headless-плана, которое имеет
смысл: без session broker, транзакций и второго authoring-хоста.

## 7. Метрики

- **Время от просьбы пользователя до проверенного изменения** (агент дописал, `pix3 check`
  зелёный, при MCP — `game_run` прошёл на версии с `matchesDisk: true`); цель медиана ≤ 30 с.
  Отдельно, не смешивая: холодная установка (`npx`, пикер) и однократные разрешения (папка, LNA,
  генерация).
- Доля прогонов, где `pix3 check` зелёный с первой попытки; среднее число итераций до зелёного.
- Вопросы агента до первого показанного изменения (цель 0).
- Ручные правки, **потерянные безвозвратно** (цель 0, жёстко) и **заменённые без плашки** (цель 0,
  жёстко); отдельно — число сигналов устаревшей записи на сессию (сигнал, что kit плохо учит
  перечитывать).
- Доля «тюнинговых» просьб, которые человек в итоге сделал мышкой — качественно, по сессиям.

## 8. Смежный трек: скорость встроенного агента

Не в скоупе этого плана, но причины найдены там же и чинятся дёшево (владелец —
[prompt-to-playable-flow.md](prompt-to-playable-flow.md) / [flow-autopilot.md](flow-autopilot.md)):

- вопросы предписаны промптом: `agent-skills/idea-stage.md` §3 «End the turn with a question» —
  перевернуть на «сначала рецепт и первый кадр, вопрос после»;
- дефолт bridge-модели — `claude-opus-5-5` (`ClaudeBridgeLlmProvider.ts`), низкий reasoning только
  во Flow — для хопов Flow дефолт Sonnet / `low`;
- в каждый запрос уходят все ~50 схем тулов и большой системный контекст — сузить набор по стадии;
- verify-гейт до 3 попыток и нуджи дают ~26 хопов на инкремент — см. verify rider в
  [agent-one-shot-generation.md](agent-one-shot-generation.md).

Agent kit (§5 B) и эти правки должны говорить одно и то же: одни правила для обоих агентов.

## 10. Риски и открытые вопросы

1. **Качество ручного YAML.** Всё держится на kit и строгом `validate`. Фаза 0 это проверяет
   первой; запасной ход — `pix3 node add/set` в CLI (типизированные правки файла), если агенты
   системно ломают формат.
2. **`SceneLoader` в Node** может потянуть canvas/WebGL-зависимости. Фолбэк — строгий профиль по
   схеме и ссылкам без инстанцирования нод (схемы свойств доступны статически).
3. **Гонка записи.** Решение и остаточный риск — §4.3: окно между проверкой и записью может стоить
   агенту записи (ловится барьером и журналом сервера), неоднозначность «сознательный возврат vs
   устаревшая запись» решается в пользу человека и видна в merge-log. Если сигналов устаревшей записи на сессию
   много — это сигнал доработать kit, а не вводить блокировки.
4. **Трёхсторонний merge по свойствам** для вложенных структур (массивы, кривые анимаций,
   ключи локализации): в v1 такие свойства сравниваются целиком, разбор — на уровне свойства.
5. **Нагрузка опроса дерева и хешей** на больших проектах — бюджет на число файлов, хеш только
   для изменившихся по mtime/размеру, иначе только открытые сцены + каталоги `scenes/`, `scripts/`.
6. **Kit устаревает с движком.** Лечится генерацией из источников + `pix3 kit --update` +
   версия kit в `pix3project.yaml`, которую `check` сверяет с версией CLI; закрепление версии в
   MCP-конфигурации и номер протокола (§5 A, §1.2).
7. **Где держать шаблоны**: переехать ли `src/templates/projects/` в пакет CLI (а редактор импортирует
   оттуда) или паковать копией при сборке. По умолчанию — копия при сборке, решить в фазе 1.
8. **Local Network Access** — механизм новый и меняется от версии к версии Chrome; фаза 0
   проверяет его в установленном PWA. Если long-poll к loopback окажется ненадёжным — короткий
   опрос с тем же протоколом.
9. **Размер `npx`-установки** CLI со вшитым TypeScript (~десятки МБ) — один раз на версию;
   мерить в холодной установке, не в основной метрике.
