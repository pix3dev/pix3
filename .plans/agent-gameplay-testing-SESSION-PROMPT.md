# Session prompt — агентское тестирование геймплея: остаток работ

Промпт для новой сессии. Читается холодным: всё, что нужно, либо здесь, либо по ссылкам.

## Что это

Ветка `feat/agent-gameplay-testing` реализует план
[agent-gameplay-testing.md](agent-gameplay-testing.md) — как встроенный AI-агент играет в
проверяемую игру и что получает на выходе. **Прочитай в плане `## 11. Журнал реализации`** — там
состояние по фазам, найденные дефекты и остаток. Остальные разделы читай по нужде через grep, не
целиком: план ~1200 строк.

**Все 9 фаз (0–8) реализованы.** Базовая линия проверки на момент передачи:

```bash
npx vitest run          # 3330 passed, 1 failed
npm run type-check      # чисто
```

Единственное красное — **`recipe-bouncer-2d: design/recipe.md fits the agent prompt budget`**
(8121 против капа 8000). Оно было красным **до** этой работы, файл не трогали. Не чини его походя:
сокращение рецептов — открытый пункт Flow §11.3 и отдельная работа.

> Если видишь второе красное — `minigame-2d: design/tests … matches the fixed format` — значит
> откатился фикс CRLF-хрупкости гарда в `recipes.spec.ts` (журнал §11, пункт 6). Интент
> `open-settings` зарегистрирован; падал сам гард.

## Что осталось

### 1. Живая проверка фазы 8 — единственная незакрытая работа, и она первая

Фаза 8 (бот-политика) написана и покрыта спеками, но **не проверена в браузере**: MCP-браузер был
занят живой сессией редактора пользователя, а убивать её ради теста нельзя. Непроверенным остаётся:

- **путь компиляции целиком** — `buildEntryModule` → настоящий esbuild → blob-import. В vitest
  blob-import не работает, поэтому спека закрывает всё до него и то, **что передано компилятору**;
  сам импорт не исполнялся ни разу;
- **фактический однокадровый лаг актуаторов** — контракт «наблюдай кадр N, действуй за N+1» выведен
  из того, что `InputService.beginFrame()` подменяет `pending*`-буферы, но не измерен.

Как проверять (начни с самого простого и наращивай):

```js
// 1) политика, которая только логирует и жмёт одну клавишу
await window.__PIX3_DEBUG__.agentTools.execute('fs_write', {
  path: 'design/tests/bots/probe.ts',
  content: `export default {
  name: 'probe',
  tick(bot) {
    bot.log('frame ' + bot.frame);
    if (bot.frame === 2) bot.press('Key_ArrowLeft', 10);
    if (bot.frame >= 30) bot.done(true, 'probe finished');
  },
};`,
});
await window.__PIX3_DEBUG__.agentTools.execute('game_run', { bot: { name: 'probe' }, maxFrames: 60 });
```

Что смотреть в ответе: `bot.frames` ≈ числу кадров прогона (если 0 — кадровый хук не приезжает);
`bot.sent` = 1; `verdict` начинается с `BOT PASS probe [physical-input]`; `bot.log` содержит строки с
номерами кадров. Затем — политика, которая жмёт клавишу и проверяет, что герой поехал (`nodeMoved` в
`until` рядом с ботом), и политика с `axis` на сцене с живым `Joystick2D`: там проверяется физическое
отклонение стика (события идут на `pointerId` 21+). Отдельно стоит увидеть отказ: `axis` на оси,
которую никто не пишет, должен вернуться строкой про «no keyboard-to-axis binding» в `bot.log`, а
прогон — `bot-idle`, а не пас.

**Прибирайся за собой**: удаляй пробные файлы (`design/tests/bots/probe.ts`, `design/tests/reports/*`),
возвращай `game_time` в `realtime`, снимай паузу, оставляй редактор играбельным. Проект в браузере —
живой проект пользователя.

### 2. Решения, которые ждут человека

1. **История ветки.** В рабочем дереве работает автокоммиттер (внешний процесс, хуков в репозитории
   нет). На ветке лежит чужой коммит по экспорту от параллельной сессии (`ResourceManager`,
   `PlayableHtmlBuildService`), а плановые документы закоммичены под сообщением «Refactor code
   structure for improved readability». Решить: чистить историю или оставить.
2. **`recipe-bouncer-2d/recipe.md`** — см. выше.
3. **Привязка регрессионных трасс к verify-гейту Flow** (§10 плана, вопрос 6). План говорит «прогонять
   сохранённые трассы после каждой правки», но с гейтом это явно не связано.
4. **`game_run` в collab-сессии** (§10, вопрос 7). Второй пользователь правит сцену во время прогона —
   исход становится непрочитываемым. Минимум: детект правки за окно прогона и пометка прогона
   загрязнённым; лок сцены — отдельное решение.

### 3. Мелочи

- **Индекса политик в системном промпте нет** (у рутин он есть, §5.7.2). После компакции агент узнаёт
  о боте только из `fs_list design/tests/bots`. Осознанное решение по объёму; первый кандидат на
  добавление, если политик станет больше двух-трёх на проект.
- `sceneId` в журнале достижимости берётся из `appState.scenes.activeSceneId`, то есть из сцены, с
  которой **начался** play; после внутриигровой `changeScene` контрол журналируется под стартовым id.
  Ложного доказательства не даёт (цепочка предков сравнивается точно), но истинный live-id жил бы в
  `GamePlaySessionService`/`SceneRunner`.
- `open-store` в playable-шаблонах **осознанно не** зарегистрирован командой: это подшаг `cta-click`,
  и отдельный диспатч означал бы второй вызов открытия магазина, то есть двойную аналитику на одном
  нажатии. Команды выражают намерения игрока, а не внутренние шаги.
- Клик monkey, меняющий сцену, внутри `manual`-прогона не приземлится: загрузка сцены асинхронна по
  настенным часам, а 120 кадров стоят ~90 мс. Переходы сцен требуют шага `game_input` в `realtime`.

## Как проверять — живьём, обязательно

Юнит-тестов недостаточно: **единственный дефект, найденный не тестами, а живой проверкой**, был из
самых серьёзных — `game_run` обещал в отчёте паузу, а правило фокуса в `GamePlaySessionService`
снимало её из его же `finally`, и поле `leftPaused` при этом врало, потому что писалось из намерения,
а не из факта. Ни один юнит-тест такого не поймал бы: дефект жил на стыке с play-режимом редактора.

Как гонять живьём:

```bash
npm run dev            # порт 8123
```

Редактор открыть в Chrome под `chrome-devtools` MCP, тулы дёргать так:

```js
await window.__PIX3_DEBUG__.agentTools.execute('game_run', { until: [{ kind: 'frames', n: 45 }] });
```

Доступны: `play_start/stop/restart/status`, `game_time`, `game_run`, `game_controls`, `game_input`,
`game_observe`, `game_trace`, `fs_read/fs_write/fs_delete`. Проверяй **данными и состоянием**, а не
скриншотами; скриншот — только для визуала и только игровой области.

Если MCP отвечает `The browser is already running for …chrome-profile`: браузер занят другой сессией.
**Не убивай его** — там живой редактор пользователя с открытым проектом. Либо договорись с
пользователем, либо отложи живую проверку и скажи об этом прямо.

## Операционные уроки (не переучивайся заново)

1. **Проверяй утверждения агентов, особенно про среду.** Два разных агента заявили, что vitest не
   работает через Bash-инструмент из-за унаследованной `ELECTRON_RUN_AS_NODE=1`. Проверено: **ложь** —
   переменная действительно выставлена, но тот же спек проходит через Bash байт в байт как через
   PowerShell. Настоящая причина «No test suite found» почти всегда искажение пути в аргументе.
2. **Проверяй и заявленную базовую линию.** Переданный промпт обещал «1 failed», в реальности их было
   два: второй — CRLF-хрупкий гард, падающий только на Windows-чекауте. Способ проверки, который не
   врёт: `git stash push -u`, прогон, `git stash pop`. Не «похоже, это не моё» — а доказано.
3. **Один файл — один писатель.** Держи за собой общие файлы (`AgentToolRegistry.ts`) или отдавай их
   ровно одному агенту. И помни: агент, сообщивший о «фоновой работе», может приземлить правки
   **после** своего завершения — пустое дерево сразу после отчёта ничего не доказывает.
4. **Задавай границу объёма явно.** Все потерянные ходы случались там, где задание допускало
   толкование размера: агент начинал проектировать подсистему вместо того, чтобы дописать поле.
   Формулировка, которая работает: «это работа на несколько десятков строк плюс спеки, а не
   подсистема; если задача выглядит больше — значит ты вышел за скоуп».
5. **Шаблоны — это то, с чего агент копирует.** Расхождение примера и кода там дороже любой другой
   несогласованности: два примера рутин, написанные параллельно в фазе 0, разошлись, и один из них
   вызывал метод компонента напрямую — то есть учил обходу, который вся конструкция запрещает. Теперь
   дрейф заблокирован структурно (`Record<keyof GameInputStep, true>`, прогон всех рутин всех
   шаблонов через настоящий парсер в `recipes.spec.ts`, а для контракта бота —
   `pix3-test-bot-dts.spec.ts`, читающий интерфейс с диска) — **не ослабляй эти страховки**.
6. **Не размывай инвариант лестницы каналов** (§5 плана): семантический вызов проверяет всё после
   «точка внутри», физический доказывает саму эту посылку, командный проверяет логику намерения. Каждый
   уровень доказывается уровнем ниже **один раз**. Соблазн «просто вызвать обработчик» возвращается
   постоянно и обнуляет проверку. У бота этот соблазн называется `channel: 'direct-action'`.
7. **Отчёт не должен врать даже в мелочи.** На честности отчёта стоит всё остальное: поле, писавшееся
   из намерения вместо факта, было опаснее самого дефекта паузы.
8. **Вынеси геометрию туда, где её можно судить спекой.** Дефект `raycast` в фазе 8 (рекурсивный
   `Box3.setFromObject`, из-за которого луч всегда попадал в корень сцены) не давал ни исключения, ни
   строки в отчёте — сенсор просто всегда отвечал одно и то же. Нашла его спека на настоящих нодах
   рантайма, появившаяся только потому, что геометрию вынесли из сервиса в отдельный модуль.
