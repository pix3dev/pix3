# Flow — «вау-пол» T0 (контракт реализации)

Цель: первый кадр Flow-проекта и первые ходы агента выглядят «дизайнерски» (уровень
референса «CYBERPINBALL» из Gemini), **не тратя токены агента**. Вау — детерминированный
(рецепт + экспандер), сочность для агента — one-liner'ы движка, а не сессии написания
кода. Источник решений: разбор 2026-08-13 (Fable): вау-разрыв с one-shot HTML-генераторами
не модельный, а бюджетно-архитектурный — ~70% их вау это статическая косметика (glow,
шрифты, хром HUD, синт-звук), которую можно и нужно печь в рецепты.

Контрольный прогон после реализации: промпт «сделай неоновый пинбол» во Flow.

## 0. Проверенные факты движка (закладываться, не перепроверять)

1. **Bloom/vignette на 2D уже работают.** `PostProcess` с `affect2D: true` маршрутизирует
   2D-слой через `EffectComposer` (`SceneRunner.ts` ~1037–1063, путь для pure-2D сцен /
   playable ads). Рецепту достаточно узла `PostProcess` в сцене — движок трогать не надо.
2. **HUD (`CanvasLayer2D`) рисуется ПОСЛЕ пост-обработки** и никогда не блюмится
   (`SceneRunner.ts` ~1127–1133). Это фича (читаемость), glow для HUD-текста делаем в
   самом `Label2D` (канвасный рендер — `ctx.shadowBlur`/`strokeText`), не блумом.
3. **Label2D рендерит текст через canvas 2D** (`label-text-layout.ts`, `ctx.font`) —
   glow/outline добавляются в отрисовку дёшево.
4. **`AudioService.play(buffer: AudioBuffer)` существует** (+ шины master/music/sfx,
   `AudioApi` — фасад `scene.audio`). Процедурный SFX = пре-рендер пресета в
   `OfflineAudioContext` → кэш `AudioBuffer` → `play` на шину `sfx`. Ассеты не нужны.
5. **`ColorRect2D` — только плоский цвет.** Градиентный фон = бейкнутый почти-белый
   градиентный PNG-плейсхолдер + существующий `core:tint` (тинт-конвейер экспандера уже
   перекрашивает почти-белые PNG палитрой брифа).
6. **JuiceApi уже даёт** `shake` / `punchScale` / `flash` + `scene.time.hitstop`; рецепты
   их уже вызывают в `TouchRules`. Дыры: частицы-burst, floating text (попапы очков), SFX.
7. 2D draw order — иерархический (`assign2DRenderOrder`), текстуры 2D — через
   `configure2DTexture()` (см. CLAUDE.md «2D overlay rendering»). Любые спавнящиеся
   рантайм-визуалы обязаны попадать в `LAYER_2D` и жить в дереве 2D-нод.

## 1. Анти-скоуп фазы

- НЕ делаем полноценный нод `Particles2D` (schema/YAML/inspector/editor-proxy) — только
  runtime-API + behavior (см. A1). Нод — отдельная фаза, если примитив приживётся.
- НЕ делаем HTML/JS-референсы перед движковой версией (решение разбора: продуктовый
  анти-паттерн).
- НЕ трогаем формат `design/progress.md`, каталог рецептов, гейты харнеса
  (verify-гейт, кноб-лимит, effort) — они работают.
- НЕ поднимаем версии пакетов, не публикуем yalc (DeepCore не затронут).

## 2. Блок A — рантайм-примитивы сочности (`packages/pix3-runtime`)

Всё ниже — **runtime-only визуалы времени play**: без YAML-сериализации, без
editor-proxy, без инспектора (кроме A4). Паттерн — как у существующих juice-эффектов.

### A1. `scene.juice.burst(target, options)` — 2D-частицы одним вызовом

- Сигнатура: `burst(target: JuiceTarget | {x,y}, options?: BurstOptions)`;
  `BurstOptions ≈ { count?, speed?, spread? (рад, default 2π), lifeSec?, color? | colors?,
  sizePx?, gravityY?, fadeOut? }` — все с дефолтами, чтобы `burst('bumper-a')` уже был красив.
- Реализация: один короткоживущий объект в 2D-слое (instanced quads или `THREE.Points`
  с круглым спрайт-материалом), обновление в тике сцены, автоуничтожение по концу жизни.
  `LAYER_2D`, `depthTest: false`, renderOrder — поверх контента ноды (см. §0.7; допустимо
  `userData[OVERLAY_2D_FLAG] = true`, если частицы должны рисоваться над детьми цели).
- Плюс behavior **`core:BurstOnSignal`** (по образцу `FreeOnSignalBehavior`/
  `PlaySoundBehavior`): config `{ signal, count?, color?, ... }` — слушает сигнал на своей
  ноде и вызывает burst в её позиции. Зарегистрировать в `register-behaviors.ts`.
- Юнит-тесты: burst создаёт и убирает объект; опции клампятся; behavior подписывается и
  отписывается.

### A2. `scene.juice.floatText(text, options)` — всплывающие очки

- Сигнатура: `floatText(text: string, options?: { at?: JuiceTarget | {x,y}, color?,
  fontSizePx?, driftPx? (default вверх ~60), durationSec? (default 0.8), glow? })`.
- Реализация: временный `Label2D` (или канвас-спрайт) в 2D-слое: подъём + fade,
  автоуничтожение. Не участвует в пикинге.
- Юнит-тест: спавн/автосмерть, дефолты.

### A3. `scene.audio.sfx(preset, options?)` — процедурные SFX без ассетов

- Пресеты (enum): `tap, score, bounce, explosion, powerup, win, lose, laser, tick`.
  Референс звучания — WebAudio-синты из one-shot HTML-игр (осциллятор + огибающая:
  square/sine/sawtooth, exponentialRamp).
- Реализация: `SfxSynth` в `core/` — лениво рендерит пресет в `AudioBuffer` через
  `OfflineAudioContext` (кэш по пресету+pitch), играет через существующий
  `AudioService.play` на шину `sfx`. `options ≈ { volume?, pitch? (полутона или множитель) }`.
  В headless/тестах (нет AudioContext) — тихий no-op, не throw.
- Плюс behavior **`core:SfxOnSignal`** (config `{ signal, preset, volume? }`).
- Юнит-тесты: пресет отдаёт буфер (с моком контекста), кэш работает, no-op без контекста.

### A4. Label2D: `glowColor`/`glowStrength`, `outlineColor`/`outlineWidth`

- Новые свойства + `getPropertySchema()` (см. `docs/property-schema-reference.md`),
  отрисовка в канвасном рендере лейбла: outline = `strokeText` подложкой, glow =
  `ctx.shadowColor/shadowBlur` (несколько проходов при `glowStrength > 1`).
- Сериализация в YAML как обычные props; дефолты = выключено (обратная совместимость:
  существующие сцены не меняют вид). Учесть паддинг канваса под blur (текст не обрезать).
- Юнит-тест: layout учитывает паддинг; schema содержит новые поля.

### A5. Документация

- `docs/nodes-and-systems.md`: JuiceApi (+burst/floatText), AudioApi (+sfx), новые
  `core:*` behaviors — в каталог.
- `docs/node-types-reference.md`: новые свойства Label2D.

## 3. Блок B — неон-переделка `recipe-bouncer-2d` (T0-вау)

Фокус — bouncer (контрольный прогон — пинбол). Паттерн переносить на arena/tapper
СЛЕДУЮЩЕЙ итерацией, не в этой.

### B1. Сцена `main.pix3scene`

- **Фон**: новый почти-белый радиальный градиент `sprites/ph-bg.png` (центр светлее) как
  `Sprite2D` на весь вьюпорт + `core:tint` → палитра брифа красит его. `game-background`
  (ColorRect) остаётся подложкой самого тёмного цвета.
- **`PostProcess`-узел**: `affect2D: true`, bloom (умеренный: threshold ≥ ~0.55, чтобы
  светились только яркие акценты) + лёгкая виньетка. Тюнабл `bloomIntensity` объявить в
  recipe.md.
- **Неон-акценты геометрии**: тонкие яркие рамки-полоски (ColorRect2D) по периметру борда
  и вокруг бамперов — то, что цветёт под блумом.
- **HUD**: `score-label`/`time-label` и заголовки — glow из A4, аккуратный
  `fontSize`-контраст (крупный счёт). `lives-bar` оставить.
- **Попапы и частицы**: `TouchRules` при score → `scene.juice.floatText('+100', …)` +
  `scene.juice.burst(...)` в точке `ball-hit`; drain → shake+flash (уже есть) + burst.
- **Звук**: в `TouchRules`/`GameRules` — `scene.audio.sfx('bounce')` на paddle/wall,
  `'score'` на bumper, `'lose'` на drain, `'win'`/`'lose'`-джинглы в `finish()`.
  Поля `scoreSound`/`damageSound` (ассетные) не ломать: ассет, если задан, приоритетнее синта.
- Juice-числа по умолчанию поднять до «сочно»: punchScale заметнее, hitstop ~40–60 мс на
  бампере.

### B2. `menu.pix3scene`

- Крупный титул (title из брифа уже патчится в `title-label` — сохранить id) с glow,
  пульсация через `core:Sine`/`core:PopIn`, тот же градиентный фон + PostProcess.

### B3. `design/recipe.md`

- Обновить: Node map (PostProcess, bg), Placeholders (+`ph-bg.png`, role `background`),
  Tunables (+`bloomIntensity`, juice-числа, sfx on/off если понадобился), Extension points
  (частицы/floatText/sfx — «one-liner, вызывай вместе с механикой»), Do not touch
  (id PostProcess-узла). Держать < 8 КБ (`MAX_RECIPE_MD_CHARS`).
- Контракт-спека рецепта (vitest, парсит tunables → ноды/схемы) обязана остаться зелёной;
  новые тюнаблы — покрыть ею же.

### B4. Критерий T0

Создание Flow-проекта из bouncer БЕЗ единого хода агента даёт кадр: градиентный фон,
светящиеся бамперы/рамки, glow-HUD, заголовок; при отскоке — звук + punch + частицы.
Проверка: `play_start` + скриншот + слух, вручную.

## 4. Блок C — планнер/экспандер (`src/services/flow/`)

### C1. `theme` в брифе + style-паки экспандера

- `PrototypeBriefStyle` + `theme?: 'neon' | 'pastel' | 'retro' | 'minimal'` (планнер
  выбирает из промпта; дефолт по жанру рецепта — bouncer → neon).
- Экспандер: `record<theme, патчи>` — детерминированный набор поверх тюнаблов рецепта
  (bgColor/boardColor, bloomIntensity/вкл-выкл, glow-цвета HUD-тюнаблов). Патчи только
  через уже объявленные tunables рецепта — никаких слепых правок YAML.
- Планнер-промпт: добавить поле в JSON-шаблон + одну строку правил. Валидация: неизвестная
  тема → дефолт + note (паттерн `validateBrief`).

### C2. `increments[0]` = отличие от скелета + секция wow

- Правило планнера (PLANNER_SYSTEM_PROMPT) переформулировать: рецепт УЖЕ играется
  (меню → игра → win/lose, управление, счёт); инкременты обязаны РАСШИРЯТЬ его. Первый
  инкремент — механика, делающая игру собой («флипперы» для пинбола, «grid-движение и
  рост» для змейки), НЕ «controls + core loop».
- В бриф — `wow?: string[]` (2–4 жанровых спектакль-элемента: множитель, tilt,
  комбо-попапы…). Экспандер дописывает их в `design/progress.md` поздними `- [ ]`
  пунктами (формат чек-листа не менять). Валидация — как у `increments`.

### C3. `flow-increment.md` — 3–4 строки, не больше

В §6 (или рядом): «Сочность дешёвая: `scene.juice.burst/floatText`, `scene.audio.sfx`,
glow-свойства Label2D — one-liner'ы. Добавляй звук/частицы/попап СРАЗУ вместе с механикой,
которую строишь, а не отдельным поздним инкрементом». Скилл не раздувать.

## 5. Порядок работ и проверки

1. Блок A и блок C — независимы (разные деревья файлов), можно параллельно.
2. Блок B — после A (использует burst/floatText/sfx/glow).
3. Общие ворота: `npm run lint`, `npm run type-check`, `npm run test` — зелёные;
   контракт-спеки рецептов зелёные; существующие сцены/Studio не меняют поведения
   (glow/outline по умолчанию выключены, PostProcess — только в файлах рецепта).
4. Контрольный прогон (вручную, после мерджа): Flow, промпт «сделай неоновый пинбол» —
   T0 по критерию B4, первый инкремент агента — флипперы, feel добавляется по ходу.

## 5½. Выводы контрольного прогона (2026-08-13, «сделай неоновый пинбол»)

Прошло: планнер выбрал bouncer + neon, первый инкремент — флипперы, wow-биты в плане,
T0 выглядит как референс (glow-титул, неоновый борд, bloom), JuiceBurst живёт в игре,
ошибок ноль. Провалилось по существу: **агент доказал механизм, а не функцию** —
«клавиша двигает флиппер» подтверждено, но пивоты стояли близко к центру, бока
открыты, мяч дренится в обход, каждый ран умирает за ~3 с без ввода.

Системный ответ (жанро-независимый, реализовано сразу):
- `flow-increment.md` §2: «recall the real one» — перед структурным инкрементом
  вспомнить каноничную геометрию жанра и записать 2–3 ограничения в decisions.md;
- `flow-increment.md` §3: «prove the FUNCTION, not the mechanism» — прогон без ввода
  vs прогон с вводом; управляемый обязан измеримо переживать неуправляемый;
- Verify рецепта = контракт играбельности, который наследует любой инкремент
  (bouncer: «защитник закрывает все пути вниз; мяч выходит только через задуманный
  зазор; свежий ран без ввода живёт несколько секунд»).

Харнес-фоллоу-апы (следующая итерация, не в этой фазе):
1. **Автозамер baseline после геймплей-мутации**: verify-гейт сам снимает короткий
   `game_observe` без ввода и вшивает в ход «run ended in 2.1s unattended (was 9s)» —
   регрессия, которую модель не может проигнорировать.
2. **Динамический effort**: структурный инкремент (новые ноды/замена скрипта) идёт
   на дефолтном effort, твики — на `low`; наивная геометрия флипперов — вероятный
   артефакт глобального `low`.

## 6. Ограничения для исполнителя

- `AGENTS.md` — обязателен к прочтению до кода; no `any`; рантайм остаётся
  editor-agnostic (никаких импортов из `src/`).
- Пути через алиасы; новые файлы рантайма — в существующие папки (`core/`, `behaviors/`).
- Плейсхолдеры рецепта — почти-белые PNG (иначе тинт-конвейер их не красит).
- `design/recipe.md` каждого рецепта < 8 КБ; `design/progress.md` — формат не трогать.
- Никаких новых `.md` в корне; правки документации — только в существующих файлах
  `docs/` (см. Docs policy).
