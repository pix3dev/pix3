# Session prompt — замер разрыва: Vibe против one-shot HTML/JS в чате

> Вставить всё, что ниже разделителя, первым сообщением свежей сессии Claude Code в репозитории `pix3`
> (ветка `main`, чистое дерево). Всё, что выше, — записка, не часть промпта.
>
> Машина должна иметь: Node 24, свободный порт 8123, Chrome, к которому цепляется `chrome-devtools` MCP,
> и настроенный BYOK-ключ (или поднятый `tools/pix3-agent-bridge`) — без ключа Vibe-лана не поедет.

---

Проведи **Vibe-лану замера разрыва** и подведи итог по обеим ланам. Это работа **измерительная,
а не улучшательная**: ничего не чинить и не оптимизировать по ходу, кроме того, что физически
блокирует прогон. Всё найденное — записывать.

## Зачем это делается

Эталон, заданный владельцем продукта: «играбельный прототип уровня того, как мы в чате Клода или
Гемини просим сделать html/js страничку-игру». Vibe до сих пор мерили **против себя** — надо
померить против эталона, потому что от результата зависит порядок трёх рычагов: **покрытие**
(идея вне каталога рецептов), **темп** (минуты хода против секунд генерации), **шеринг**
(публикации нет вообще).

## Шаг 1 — окружение

```bash
npm ci                      # Node 24 обязателен
npm run dev                 # порт 8123
```

Подцепись `chrome-devtools` MCP к Chrome, открой `http://localhost:8123`.

**Провайдер**: по возможности выставь **тот же** `claude-sonnet-5` (лана моста «Claude Code (MAX)»),
чтобы сравнение было по одной модели. Прочти эффективного провайдера **из
`AgentSettingsService.getSelectedProvider()`**, а не из `prefs.selectedProviderId` — они расходятся.
Фактическую модель обязательно запиши в журнал: если она не та, вывод про темп станет условным.

## Шаг 2 — четыре прогона Vibe

Промпты **дословно те же четыре**: `тапалка про монетки`, `змейка`, `флоппи-бёрд`, `тетрис`.
Никаких уточнений, никаких подсказок про жанр — эталон их тоже не получал.

Для каждого промпта:

1. **Свежий проект каждый раз.** Бэкенд `browser` (OPFS) — он не требует нативного пикера папки,
   которым CDP не умеет рулить.
2. С экрана Welcome ввести промпт как обычный пользователь (`pix3-welcome`, prompt-hero) — **не**
   вызывать `startIdea`/`startPrototype` напрямую. Мы меряем пользовательский путь.
3. Засечь три момента:
   - `t_idea` — редактор идеи готов (входа в LLM тут нет, должно быть быстро);
   - `t_first` — после «Start prototype» на стейдже первый кадр, в который можно ткнуть;
   - `t_done` — состояние, проходящее рубрику по кор-лупу И условию конца.
4. **Кап — три хода агента.** Если за три хода `t_done` не достигнут — так и записать
   («не достигнуто за 3 хода»). Это не провал прогона, это и есть результат.
5. Записать **какой рецепт выбрал планнер** (`recipe-*`) и попал ли он в жанр. Для P3/P4 рецепта
   в каталоге нет: `FALLBACK_RECIPE_ID` — `recipe-arena-2d`, плюс есть `recipe-blank-2d`. Что
   именно выбралось — ключевое наблюдение по рычагу «покрытие».

**Откуда брать цифры** (не на глаз):

- `__PIX3_DEBUG__.agent.send(text)` резолвится по завершении **всего** хода — это wall-clock хода.
  Но для первого промпта используй UI (шаг 2.2), а `agent.send` — для последующих итераций.
- `__PIX3_DEBUG__.agent.getState()` → `iterationsUsed` / `iterationCap`, `inputTokens`,
  `outputTokens`, `cacheReadTokens`, `cacheCreationTokens`.
- `__PIX3_DEBUG__.agent.transcript(limit)` → тул-трейс: сколько вызовов, каких, сколько разведки.
- `__PIX3_DEBUG__.eval.run(spec)` — если удобнее оформить проверку кор-лупа как чек-спеку
  (`.plans/agent-eval-scenarios.md` — примеры).

## Грабли этого окружения (проверено кровью)

- **Редактор рисует по требованию.** Если меняешь three.js-объекты мимо обычных путей — дёргай
  `viewportRenderService.requestRender()`, иначе изменение появится только через ≤500 мс хартбит.
- **Unfocused Chrome под MCP морозит игровой кадр.** «Игра не работает» на скриншоте — сначала
  проверь **состояние** живых нод (`window.__PIX3_ENGINE__.getRuntimeSceneRoot()`), а не картинку.
  Общее правило этого проекта: **верифицировать состоянием, скриншот — только для визуала.**
- `game_input` длинным `ms` не рулит — направление меняет короткое нажатие (~120 мс).
- Тул `create_node` **автосохраняет сцену**; после экспериментов не оставляй мусор в чужих проектах.
- Порт **4173** отдаёт закешированный редактор из service worker'а другого проекта — превью
  поднимай на другом порту.
- Остановка фонового dev-процесса требует **дочернего** pid, а не обёртки `npm`
  (`netstat -ano | grep LISTENING | grep :8123`, потом проверить командную строку процесса).
- На Windows/ARM `npx vitest` требует `--pool=threads`.
- **Русский текст через argv нативных .exe в Bash-инструменте корёжится** — из-за этого чат-лана
  сначала получила ложный `refusal` и жалобу на кодировку. Любые запросы с кириллицей собирай и
  отправляй целиком из Python с явным UTF-8 (образец — `measurements/chatlane.py`).
- Известный дефект моста, на замер не влияет, но не пугайся: `usage.output_tokens` у agent-SDK-ланы
  возвращает 2–8 на ответ в 8–12 КБ. Токены этой ланы считать нельзя, время — можно.

## Чего НЕ делать

- Не чинить найденные баги харнесса (кроме блокирующих прогон) — записывать в журнал.
- Не улучшать рецепты, промпты планнера и скиллы «по ходу»: любое такое изменение обнуляет
  сравнимость с чат-ланой, снятой сегодня.
- Не подсказывать агенту жанр и не переформулировать промпт, если он выбрал «не тот» рецепт —
  это измеряемое поведение, а не помеха замеру.
