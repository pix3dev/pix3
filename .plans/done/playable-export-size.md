# Размер playable-экспорта: измерение и план сжатия

Статус: **фазы 1–3 реализованы** (2026-08-13), фаза 4 — задел на потом.
Связано: [prompt-to-playable-flow.md](prompt-to-playable-flow.md) §7.2 (публикация отдаёт тот
же артефакт), [TODO.md](TODO.md) → «add image compression option».

Отчёт о реализации: [playable-export-size-report.md](playable-export-size-report.md).

## 1. С чего начали: замер, а не догадки

Поводом стал экспорт пинбола: **1.34 MiB** HTML, из которых по size-report'у
«JS/HTML + metadata wrapper» — **1.22 MiB**, а все ассеты вместе — 124 KiB base64.
То есть оптимизировать надо код, а не картинки.

Состав кода получен воспроизведением ровно того же бандла офлайн (esbuild с алиасами из
`PlayableHtmlBuildService.createCompileOptions`); сумма совпала с отчётом экспорта
байт-в-байт (1226 KiB), поэтому цифрам можно верить:

| KiB (min) | что |
|---|---|
| 550 | three.js core build |
| 212 | `packages/pix3-runtime/src/nodes/**` — **все** ~30 типов нод |
| 119 | core-сервисы рантайма |
| 96 | парсер `yaml` (+ stringifier) |
| 65 | `core:` behaviors |
| 59 | `src/net/**` (мультиплеер) |
| 43 | `three/examples` GLTFLoader |
| 38 | SceneLoader |
| 14 / 14 / 12 | SceneSaver / shader-effects / animation |

Три вывода, которые определили план:

1. **three.js почти несжимаем tree-shaking'ом.** Минимальный бандл, который лишь трогает
   `WebGLRenderer`, — уже 491 KiB (вся библиотека шейдерных чанков). Из 550 KiB «лишних»
   максимум ~60. 45% файла нельзя убрать вычищением импортов — только компрессией.
2. **Всё регистрируется и импортируется безусловно.** `SceneLoader` статически импортирует
   каждый тип ноды (гигантский `switch`), `register-behaviors` — все 20 behaviors, `main.ts`
   безусловно создаёт `NetworkService` и `SceneSaver`, `AssetLoader` — GLTFLoader.
3. **`postprocessing` в playable вообще не попадает — и это баг.** В alias-мапе его нет, а
   `ScriptCompilerService.onResolve` любой неалиасенный bare-специфаер помечает
   `external: true`; importmap в экспортированном HTML нет → `import("postprocessing")`
   из `PostProcessingPipeline` упадёт, нода `PostProcess` молча не работает.

## 2. Закрытые развилки

**Р1. Компрессия vs размер по проводу.** Self-extracting HTML снижает **размер файла**
втрое, но канал, который жмёт сам, часть этого выигрыша съедает.
→ Решение: **опция в диалоге экспорта, по умолчанию включена** для «скачать .html» (там
бюджет — сырой файл: типовые требования playable-сетей 2–5 MB на один HTML), и **не
применяется** к zip-экспорту и к публикации.

Оценка «по проводу станет хуже на 33%» (base64(gzip) считалась несжимаемой) **не подтвердилась
замером** — см. §3.1: по gzip-каналу штраф 0.9%, и только по brotli — 21%. Решение остаётся
тем же, но обоснование другое: дефолт-«вкл» дёшев почти везде, а дорог ровно там, где канал
отдаёт brotli.

**Р2. Как исполнять распакованный код: iife + classic script.**
Не blob-URL и не `type="module"`: playable крутят в iframe с opaque origin (`data:`/srcdoc),
где module-скрипты и blob-модули блокируются. В репозитории уже есть тот же вывод —
`classicScriptCompatibilityPlugin` в `src/templates/build/vite.config.ts.tpl` срезает
`type="module"` с выхода vite ровно по этой причине. Проверено: esbuild `format: 'iife'`
инлайнит динамические импорты внутрь IIFE (`Promise.resolve().then(...)`), и результат
исполняется как обычный скрипт. Побочно: сжатый экспорт **совместимее** текущего.

**Р3. Единый механизм выпиливания — стабы через `moduleAliases`, а не рефакторинг рантайма.**
Экспорт уже владеет картой алиасов, поэтому «выпилить» модуль = отдать бандлеру заглушку
`export class X { constructor(){ throw new Error('stripped') } }`. Это даёт нулевые изменения
публичного API `@pix3/runtime` (пакет потребляет внешний проект через yalc) и никакого
дублирования метаданных (id/displayName behaviors остаются в рантайме).
Отвергнуто: «одна фабрика на тип ноды + генерируемая таблица» — 1000 строк механического
рефакторинга `SceneLoader` и риск для потребителей, при том же выигрыше.

**Р4. Критерий включения — «упомянуто где угодно».** Токенизируем все тексты сцен/префабов и
исходники скриптов проекта в один `Set` слов; тип ноды / behavior включается, если его имя
(или id вида `core:Follow`) встретилось. Это заведомо надмножество нужного: ложное включение
стоит килобайты, ложное исключение — сломанную игру. Ложное исключение остаётся возможным
только если текст сцены собирается в рантайме конкатенацией — и тогда падение будет с
внятным сообщением `[Pix3] X was stripped from this build`.

**Р5. Что пинит типы нод (важно для порядка работ).** `SceneSaver` импортирует **каждый** тип
ноды для сериализации — пока он в бандле, ни один тип выпилить нельзя. Поэтому «убрать
SceneSaver из плеера» — не 14 KiB, а *предусловие* для 116 KiB. Остаточные пины после него:
`SceneRunner` (per-frame `instanceof` по Camera2D/Particles3D/GeometryMesh/InstancedMesh3D/
Sprite3D/AnimatedSprite3D/AudioPlayer/PostProcess/Camera3D), behaviors и
`localization/apply-locale-to-tree`. Снять их — это уже замена `instanceof`-диспатча
реестром (фаза 4).

**Р6. `yaml` убираем не из рантайма, а из бандла.** Сцены и префабы конвертируются в JSON на
этапе сборки, а `yaml` алиасится на стаб `parse = JSON.parse`. Рантайм не меняется вообще,
редактор и DeepCore продолжают читать YAML. Проверено: `yaml` в рантайме импортируют только
`SceneLoader` (parse) и `SceneSaver` (stringify); локали и `.pix3anim` уже JSON.

## 3. Что даёт каждый рычаг (замерено)

Порычаговый прогон (esbuild, тот же набор алиасов; ассеты пустые, поэтому это чистый код):

| шаг | сырой JS | gzip | итоговый HTML при self-extract |
|---|---|---|---|
| 0. как было | 1226 KiB | 314 | ~0.54 MiB |
| 1. JSON-сцены (`yaml` → `JSON.parse`) | 1130 | 285 | ~0.50 |
| 2. + стаб GLTFLoader (нет `.glb` в проекте) | 1068 | 268 | ~0.48 |
| 3. + без `SceneSaver` | 1054 | 264 | ~0.47 |
| 4. + без `net/**` | 995 | 249 | ~0.45 |
| 5. + выпиливание неиспользуемых нод и behaviors | 879 | 223 | ~0.42 |

Контрольный прогон **уже реализованной продакшн-логикой** (транспилированный
`strippable-runtime-modules.ts` + настоящий esbuild, байты по метафайлу):

| конфигурация | сырой JS | gzip | yaml | net | SceneSaver | glTF | postprocessing |
|---|---|---|---|---|---|---|---|
| всё упомянуто (худший случай) | 1212 KiB | 311 | 98 KB | 61 KB | 0 | 42 KB | 0 |
| пинбол | 885 | 225 | 0 | 1.6 KB | 0 | 0 | 0 |
| пинбол + нода PostProcess | 1205 | 337 | 0 | 1.6 KB | 0 | 0 | 322 KB |

Итого: **1.34 MiB → ~0.42 MiB (−69%)** для пинбола; без компрессии — 1.34 → ~0.98 MiB (−27%).
Компрессия — самый большой единичный рычаг (−60% сама по себе), выпиливание — единственный,
который помогает и по проводу. Даже в худшем случае (ничего не выпилено) экспорт стал на
14 KiB меньше — за счёт снятого клона сцены на старте.

### 3.1. Замер живьём (Snake, 2026-08-13)

Собрано настоящим `PlayableHtmlBuildService` в открытом редакторе, оба варианта сохранены
на диск и померены `zlib` (то есть это выход продакшн-пути, а не оффлайн-реконструкция):

| вариант | файл | по gzip-каналу | по brotli-каналу |
|---|---|---|---|
| без минификации (диагностический прогон) | 2 003 765 | 406 356 | 314 772 |
| как экспортируется, без компрессии | 969 872 | 258 987 | 215 242 |
| как экспортируется, с компрессией | **347 444** | 261 325 | 259 810 |

Отсюда два вывода, меняющие формулировки в UI и доках:

1. **Минификация не заменяется gzip'ом**: 406 → 259 KiB *после* gzip, то есть минификация
   срезает ещё 36% сжатого размера. Переименование локалов и выкидывание мёртвого кода —
   не то, что делает энтропийный кодер.
2. **Штраф компрессии по проводу зависит от кодека канала**: gzip повторно упаковывает
   base64 почти без потерь (+0.9%), brotli — нет (+21%), потому что на исходном тексте
   brotli сильно лучше gzip, а внутрь готового gzip-пейлоада уже не залезет.

**Проверенные и отвергнутые микро-рычаги** (замер показал ноль, в коде их нет):
`pure: ['console.debug','console.log']` — −1 KiB (esbuild не выбрасывает вызов, у которого
аргументы могут бросить); `sideEffects: false` на модулях рантайма — 0, esbuild и так
шейкает ре-экспорты барреля; `legalComments: 'none'` — 0 (при `minify` уже так).

## 4. Фазы

### Фаза 1 — компрессия (сделано)

- `ScriptCompilerService`: опция `format?: 'esm' | 'iife'` (по умолчанию `esm`).
- `PlayableHtmlBuildService`: опция `compress`; при ней бандл собирается как `iife`,
  гзипуется `CompressionStream('gzip')`, кладётся base64-строкой в HTML с загрузчиком на
  `DecompressionStream('gzip')` + внятный фолбэк-текст для браузеров без него.
- size-report: строки про сжатый payload и про то, сколько сэкономлено.
- UI: чекбокс «Compress output (gzip self-extracting)» в диалоге выбора entry-сцены,
  по умолчанию включён; zip-экспорт чекбокса не показывает.

### Фаза 2 — выпиливание без изменения API рантайма (сделано)

- JSON-сцены + стаб `yaml`.
- Стаб GLTFLoader, если в сборке нет `.glb`/`.gltf` и никто не упоминает `GLTFLoader`.
- `virtual:runtime-network` по образцу `virtual:runtime-spine`: `main.ts` подключает сеть
  через генерируемый модуль, экспорт отдаёт no-op, если проект нигде не упоминает сеть.
- `SceneManager` принимает `SceneSaver` опционально; `main.ts` плеера его не создаёт.
- Стабы неиспользуемых behaviors и типов нод + **страж от дрейфа**: спека пересчитывает граф
  value-импортов рантайма по диску и падает, если таблица «что можно выпилить» разошлась с
  кодом.

### Фаза 3 — починка `postprocessing` (сделано)

Вендорится в бандл только когда сцена реально ставит `PostProcess` (тот же приём, что со
Spine), иначе алиасится на стаб с внятной ошибкой. Раньше в обоих случаях был битый external.

### Фаза 4 — отложено (следующий заход)

1. **Снять `instanceof`-пины в `SceneRunner`** (реестр per-type обновлений вместо
   `instanceof`) — открывает ~90 KiB: Particles3D (24), ScrollContainer2D (13),
   VirtualCamera3D (10), GeometryMesh, InstancedMesh3D, Sprite3D/AnimatedSprite3D, Camera3D.
   Это уже настоящий рефакторинг рантайма, с риском для потребителей — отдельным заходом.
2. **Компрессия ассетов при экспорте** (PNG → WebP, переиспользовать `AssetGenService`):
   `sprites/ph-bg.png` 52.9 KiB → ~12–15 KiB. Пункт из TODO.md, к экспорту не подключён.
3. **Режим «оптимизировать по проводу»**: не сжимать payload, но включить всё из фазы 2 —
   для публикации из §7.2, где gzip делает сервер.
4. **`three` под нож** — только если появится 2D-only рендер-путь; сейчас пол 491 KiB.

## 5. Анти-скоуп

- Не трогаем three.js (см. §1.1) и не тащим альтернативный рендерер.
- Не делаем code-splitting в playable: артефакт по определению однофайловый.
- Не включаем компрессию для zip и публикации — там она вредна (Р1).
- Не переписываем `SceneLoader` в таблицу фабрик (Р3).
